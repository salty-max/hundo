# Deploying

Every push, deploy and release needs the user's go, asked of the user in the session that opened the work (a child sends the question there and asks nothing itself), or in the session itself when it has no opener. That includes creating a Vercel project.

## The projects

Each guide is its own Vercel project on the team jellycat, built from this repository. The landing page for `hundo.quest` has one too, `hundo-home` ([below](#the-landing-page)). The project is named after the app's package (`hundo-koholint` for `apps/koholint`). The guide lives at `https://<sub>.hundo.quest`, attached to its project as a domain. The subdomain is chosen per guide (`koholint`, `rdr`, `echoes`) and set as `brand.home`. `hundo.quest` is registered through Vercel on the same team, so Vercel's DNS does the rest. The first three guides moved here from `*.vercel.app` addresses with the hand-off below; once their readers had moved, the old addresses were detached and `movedFrom` removed from their brands. Red Dead then moved from `reddead.hundo.quest` to `rdr.hundo.quest` the same way, and on 20 Nov 2026 `reddead.hundo.quest` was detached from `hundo-rdr` and removed from `movedFrom`. A fresh visit there gets a 404 (seen with curl, 20 Nov 2026). Not tried: a browser that still holds the old build's service worker probably keeps showing its old shell, and rdr no longer takes a hand-off from it, so progress left there would not come across. No guide lists a `movedFrom`. The root README's apps table lists the projects and their sites.

Settings that live in the Vercel dashboard rather than in the repository:

- **Root Directory:** `apps/<name>`. It covers every branch, so renaming an app's folder means changing it just before that branch is pushed and merging without delay: until the merge, `main` has no such folder and the project's builds of it fail.
- **"Include files outside the Root Directory":** on, the default. The build needs `packages/core` and the root workspace files.
- **Production branch:** `main`.
- **Node.js version:** 26.x. CI runs the same major.
- **Preview toolbar off:** the environment variable `VERCEL_PREVIEW_FEEDBACK_ENABLED` set to `0`, type plain, target Preview only, to stop Vercel injecting its toolbar into previews. Why, and how it was checked: [the toolbar pitfall](#pitfalls) below. The six guides' projects have it (read back on each, 20 Nov 2026), and so does `hundo-home` (read back when it was created, 20 Nov 2026); `hundo-api` serves no page, so it has none (read back too).

## The landing page

Its Vercel project, `hundo-home` on the team jellycat, was created on 20 Nov 2026 through Vercel's API, with its Root Directory `home` and the other dashboard settings as above: outside files on, Node 26.x and the preview toolbar's variable, read back once it was made. It is connected to the repository while its pull request is open, with `main` as its production branch, as [a new project](#a-new-project)'s steps 5 and 8 say. It is not a guide, so its `vercel.json` is its own and not the guides' file:

Its `deploy.test.ts` holds every other header to Koholint's `vercel.json`, so a change to the guides' headers fails it until home follows.
- **`/api` to the sync API, and no catch-all.** It holds no progress. The API takes `https://hundo.quest` for that route alone ([its README](../services/sync/README.md#who-may-call)). It has one page, so an unknown path is a 404, answered with its `404.html` through an `error` phase (`{ "handle": "error" }`, then the route to `/404.html` with status 404). Not tried on Vercel yet: check it on the first deployment with `curl -sI <deployment>/nope` (a 404 whose body is the page, with the CSP) and `curl -sI <deployment>/assets/nope.js` (a 404 without the year-long cache).
- **The long cache only on a hit** (`/assets/*` after `{ "handle": "hit" }`), as for the guides.
- **A link preview like a guide's**: `og:image` names `https://hundo.quest/assets/og-<hash>.jpg`, made at build by `home/src/og.ts`. As for a guide, the production address may not have a new picture yet, so on a preview read the picture's path from the preview's `index.html` and fetch `<preview-url>/assets/og-<hash>.jpg`: it should come back as a 1200×630 JPEG.

It watches `home`, `apps`, `packages/core` and the root workspace files: the page is made from every guide's files, so any guide's change rebuilds it. It isn't in `scripts/`, which every guide's ignore step watches.

The domains go on at launch, after the merge, once `main`'s production deployment of `hundo-home` is built, as for a new guide: `hundo.quest` on `hundo-home`, and `www.hundo.quest` on it too, set to redirect (308) to `hundo.quest`. ## What `vercel.json` sets

Every app's `vercel.json` is the same, and `deploy.test.ts` fails if one drifts:

- **Install:** `pnpm install --frozen-lockfile`. Run from the app folder, pnpm finds the workspace root and installs everything from the root lockfile. A lockfile that doesn't match a `package.json` fails the deploy, the same way it fails CI.
- **Build:** `pnpm build`, which is `tsc && vite build`, with output in `dist`.
- **Ignore command:** `sh ../../scripts/vercel-ignore.sh`, one script for every app. Vercel skips the build when it exits 0 and builds when it exits 1. **Any other exit code fails the deployment.** The script diffs from the last deployed commit (`VERCEL_GIT_PREVIOUS_SHA`, or the previous commit when that's empty) over the app's own folder, core, `scripts` and the root files the build reads. It answers 1 whenever it can't compare. What it answers:

  | Case | Exit | Result |
  | --- | --- | --- |
  | a commit touching only Echoes, on the Koholint project | 0 | skipped |
  | the same commit on the Echoes project | 1 | built |
  | `VERCEL_GIT_PREVIOUS_SHA` empty | 1 | compared with `HEAD^`, built |
  | the previous deployed commit no longer in history | 1 | built |

  The last case once failed all three production deploys. A bare `git diff` in the ignore command exited 128 on a commit that had been rewritten away, and Vercel treats that as an error, not a build. `deploy.test.ts` holds the script to literal exits 0 and 1, ending in `exit 1`, and to valid shell syntax. The first three rows were tried on real commit ranges with the earlier bare `git diff`, when the monorepo was set up.

  So a change to one guide deploys only that guide, and a change to core, the lockfile or the root `package.json` deploys every guide. The root `docs/`, `README.md` and `CLAUDE.md`, the harness, the ESLint config and `.github/` aren't in the list, and a commit touching only those deploys nothing. An app's own `README.md` and `docs/facts-to-verify.md` sit inside its folder, though, so editing them redeploys that guide. If the build starts to read another root file, add it to the list in every app. `deploy.test.ts` checks that core and the root workspace files stay in it.

  Vercel leaves `VERCEL_GIT_PREVIOUS_SHA` empty on a branch's first deployment ([its docs](https://vercel.com/docs/environment-variables/system-environment-variables)). So on a new branch only the last commit decides: when that commit touches only docs, no preview gets built, even if earlier commits on the branch changed a guide. Push a commit that touches the app, or, on a project that has launched (its `hundo.quest` domain on and its production built from `main`), build it with `vercel deploy` (never before: step 8 of [a new project](#a-new-project)) (a redeploy runs the same ignore command and is skipped the same way, see Pitfalls).
- **Routes only.** The file has `routes` and none of `headers`, `rewrites`, `redirects` or `trailingSlash`. Vercel runs routes in phases: what comes before the first `{ "handle": … }` runs on every request, before the file lookup; `filesystem` runs after a miss; `hit` runs after a file was found. A `headers` rule is compiled into the first kind, so it matches by path whether or not the file exists, and that is how a missing `/assets/nope.js` came back with a year of cache. Hence the long cache rules sit in `hit`, and the rest of the file is what `headers` and `rewrites` used to build, in the same order. Why not keep `headers` and add a few `routes`: Vercel puts a file's `routes` ahead of what it builds from the other properties, so a `handle` in them takes everything after it into its phase, the CSP included (seen in `vercel build`'s `.vercel/output/config.json`, 2026-11-15). Vercel's docs list `handle` among the [deprecated route properties](https://vercel.com/docs/project-configuration/vercel-json#deprecated-route-properties), but `hit` did what the [Build Output API](https://vercel.com/docs/build-output-api/configuration#handler-route) says on a real preview (see Pitfalls).
- **Before the file lookup**, on every request, 404s included:
  - a strict Content-Security-Policy, with `script-src 'self'` and no inline scripts;
  - `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` and `Cross-Origin-Opener-Policy`;
  - `public, max-age=0, must-revalidate` on `index.html`, `sw.js`, `theme-init.js` and the manifest, so a new version is seen at once;
  - `Service-Worker-Allowed: /` on `sw.js`.
- **After a miss**, two routes, in this order. `/api` and what follows it goes to `https://api.hundo.quest/api/…` (the sync API, so a call is same-origin and its cookies are the guide's own, and the CSP keeps `connect-src 'self'`). Then one catch-all sends every other path except `/api/`, `/assets/`, `/fonts/`, `/icons/` and `/workbox-` to `/index.html`, so deep links like `/guide/3` load the app. A file that exists never gets this far, which is how the root `/favicon.ico` is served.
- **After a hit**, a long cache, only for a file that exists:
  - one year `immutable` on hashed `/assets/*` and the Workbox runtime (`/workbox-<hash>.js`);
  - a week, with stale-while-revalidate, on fonts and icons (an icon's URL carries its file's version, so new art is a new URL: [core.md](core.md#the-installed-app)).

  A missing file is Vercel's plain-text 404 with `public, max-age=0, must-revalidate`.

## Pitfalls

Each of these broke something or nearly did. `packages/core/src/deploy.test.ts` checks `cleanUrls`, the catch-all, the long cache and the inline scripts in every app, and each guide's `guide.test.ts` checks the storage keys.

- **Never turn on `cleanUrls`.** It made deep links like `/guide/3` return 404, because the catch-all rewrite stopped applying (fixed in `38e8d39`).
- **Keep `/api`, `/assets`, `/fonts`, `/icons` and `/workbox-` out of the catch-all.** A request for a hashed asset from an older deploy must be a real 404. Rewritten, it gets `index.html` back in place of JavaScript. That breaks the page, and a one-year cache rule can keep the HTML cached. `/workbox-nope.js` did exactly that (seen on production, 2026-11-15): 200, `text/html`, `immutable`, and the CDN had it cached. `sw.js` imports its Workbox chunk by that name, so a stuck HTML copy would have given the worker HTML to run (an inference; not reproduced). A call to `/api` that missed would come back as the app's page, which a client reads as an answer. The `/api` route to the sync API sits before the catch-all, and `deploy.test.ts` checks both and their order.
- **A long cache comes only with a found file.** A deploy race, or an old page asking for a file from a newer build, can ask for an asset that isn't there yet. A one-year `immutable` on that 404 sticks in the browser (and [Vercel's CDN caches 404s too](https://vercel.com/docs/caching/cdn-cache#cacheable-response-criteria)), and the file stays "missing" for that reader after it exists. A `headers` rule can't tell: its `has` and `missing` match request headers, cookies, host and query only, never the status or whether the file exists. So the cache rules live in the `hit` phase of `routes` (see above). On 2026-11-15 a scratch static site (a preview of `hundo-echoes`, removed after) put four ways side by side, each against a file that exists and one that doesn't:

  | Rule | Missing file |
  | --- | --- |
  | before the file lookup, as `headers` did | 404 with the year |
  | in the `hit` phase | 404 with `max-age=0, must-revalidate` (**used**) |
  | an override in the `miss` phase | no effect |
  | an override in the `error` phase | 404 with `no-store` |

  Found files kept their rule in the `hit` phase, from the CDN on repeat requests, and with ranges and query strings. SvelteKit's adapter ran into the same ([thread](https://community.vercel.com/t/svelte-cache-404-bug/350)), and its fix ([sveltejs/kit#12530](https://github.com/sveltejs/kit/pull/12530)) has its server function set the header itself, which a static guide has no function for. The `error` phase would do as well, but it needs the long rule to be set first and then undone. `deploy.test.ts` holds the file to the phases, and `headers.sh` checks a preview's 404s. If `hit` ever stops working, `headers.sh` is what shows it, since the test only reads the file.
- **The preview toolbar is switched off in the Vercel project, because the CSP blocks its script.** Vercel injects its toolbar into a preview's page as a script from `vercel.live` (a `hundo-echoes` preview built on 20 Nov 2026, before the variable below, has `vercel.live/_next-live/feedback/feedback.js` in its HTML), and the CSP's `script-src 'self'` refuses it, so each preview's console shows one CSP error, and the toolbar can't have loaded past it (inferred from the block; nobody saw it fail to show). Production has no toolbar, so readers never saw it. It is handled in the Vercel project, not in `vercel.json`: each guide's project has the environment variable `VERCEL_PREVIEW_FEEDBACK_ENABLED` set to `0`, type plain, target Preview only (set on the six guides' projects on 20 Nov 2026 and read back on each), one of the ways [Vercel documents](https://vercel.com/docs/vercel-toolbar/managing-toolbar#enable-or-disable-the-toolbar-for-a-specific-branch) to turn the toolbar off on previews. Vercel also documents a project setting and a team setting for it (Settings, General, Vercel Toolbar, Pre-Production Deployments: Off); the variable is what was set. Allowing `vercel.live` on previews instead was weighed and not done:
  - the toolbar's [CSP section](https://vercel.com/docs/vercel-toolbar/managing-toolbar#using-a-content-security-policy) lists more than `script-src` for it (its own `connect-src` with a websocket to `wss://ws-us3.pusher.com`, `frame-src`, and image, font and style origins; it says you "may need" them), so allowing the script alone would probably trade one error for several (inferred, not tried);
  - a `has: host` route would have had to be trusted on three things not found in Vercel's `routes` docs (whether a host pattern is anchored, how `missing` behaves, which of two routes' same header wins), and the file is held to routes alone, in one order, in every guide;
  - a host can't tell every preview from every production-served address: by [Vercel's description of generated URLs](https://vercel.com/docs/deployments/generated-urls) a production deployment has a unique `<project>-<hash>-<team>.vercel.app` address of the preview's own form (not tried), so the looser CSP would have reached production deployments too. None is an address readers use, but production's CSP is the one rule here with no exceptions.

  So the CSP stays as it is, `script-src 'self'` included, on every response from every host. A new project needs the variable ([a new project](#a-new-project), step 5), or each of its previews logs the error again. A preview built before the variable was set keeps the toolbar (the `hundo-echoes` one above still had it when fetched after the variable was set), so judge the change on a preview built after. To see whether a preview has it, from a folder linked to the project as in [Preview first](#preview-first): `vercel curl / --deployment <preview-url> --scope jellycat -- -s | grep -oE 'vercel\.live[^"]*|/theme-init\.js' | sort | uniq -c`. The page's own `/theme-init.js` must show once, which proves the page came back (from any other folder it is a 302 with neither); the `vercel.live/…/feedback.js` line is absent on a preview built after the variable. On the pre-variable `hundo-echoes` preview both lines showed. On `hundo-pharloom-o8imvzfz1-jellycat.vercel.app`, a preview of the branch `claude/vigorous-wescoff-0d639c` created 20 Nov 2026 at 09:17 UTC (the variable on `hundo-pharloom` at 08:50 UTC, the deployment's `createdAt` and the variable's read back from the API), only `1 /theme-init.js` showed. So the variable applies to every preview, though Vercel documents it for a single preview branch and none is set here. Whether the console on such a preview is free of CSP errors was not looked at in a browser.
- **No inline scripts.** The CSP forbids them, so `theme-init.js`, which sets the theme before first paint, stays an external file. Don't fold it into `index.html`, and don't add `'unsafe-inline'` to make something work.
- **Storage keys never change, and an address changes only with a hand-off.** Progress lives in the reader's browser, in localStorage, under `<storagePrefix>.v1`, and localStorage belongs to one origin, so a new prefix or a bare redirect starts every reader from nothing. Each guide's `guide.test.ts` pins its full keys. To move a guide:
  - set `brand.home` to the new address and list the old hostnames in `brand.movedFrom`;
  - attach the new address to the project and check it serves before the merge, or the redirect lands on nothing;
  - keep the old address attached and serving.

  On every visit there, `packages/core/src/boot.ts` redirects to the same page on `home`, with the saved progress and theme in the URL fragment. The new address imports them only when the visit came from an old address and it has no checks yet. `boot.test.ts` covers it.
- **Connect a repository to a project only once its Root Directory exists on `main`.** Until then every branch without that folder fails its deployment at clone with "The specified Root Directory … does not exist", and each of those pull requests shows a failing check. On `hundo-api`, neither an ignore command (none gets to run) nor `gitProviderOptions.createDeployments` (it only concerns GitHub's deployment notifications) stopped it. Disconnecting the repository did (`vercel git disconnect`). For a new guide that cost is accepted while its pull request is open, because its first deployment comes from Git (step 8 of [a new project](#a-new-project)): connect the project once the guide's pull request is open, and until the merge other branches' pushes show a failed deployment on it.
- **The ignore command can cancel a deployment you want.** It answers 0 whenever the watched diff is empty. On `hundo-api` an API deployment, a redeploy, and an API deployment with the ignore command overridden in its `projectSettings` were all canceled with "The Ignored Build Step command returned exit code 0", for a commit the branch had already deployed. The script must have been handed that earlier deployment's commit as `VERCEL_GIT_PREVIOUS_SHA` (an inference: against `HEAD^` it would have found the new folder changed), and the `ignoreCommand` in `vercel.json` won over the override. `vercel deploy` from a linked repository root built it.
- **A project whose git deployments were all skipped never gets `VERCEL_GIT_PREVIOUS_SHA`, so only a push's last commit decides.** `hundo-api`'s production deployment was made by hand (`vercel deploy --prod`, which names no commit). After the sync merge, every git deployment on `main` of that project was canceled by its ignore step with exit 0: three docs-only commits, and the component base's merge, whose `pnpm-lock.yaml` change sat earlier in the push than its docs-only last commit. Run with the variable empty, the script answers 0 for each of those tips (and 1 for #14's whole range, given a previous SHA), so what Vercel passed was probably empty (inferred: a deployment that never built leaves no "last successful" commit). The service's script now builds whenever the variable is empty, and `project.test.ts` runs it against real history. The guides' script still compares with `HEAD^` there. It's right once a git build has succeeded, which sets the variable (inferred, and the first push to a new branch still shows only its last commit, see above).
- **A deploy reaches a reader's open or installed guide at its next quiet start, or when they accept the update prompt.** The service worker registers with `registerType: "prompt"`, and the page looks for a new build when it comes back to the screen and once an hour ([core.md](core.md#syncing-devices)). A build found while the guide is only just starting (nothing touched in the first 20 seconds, no dialog, no other tab of the guide in use) takes over by itself: the page reloads once on the new build. One found later waits for "Reload" on "A new version of the guide is ready". Before this, on 15 Nov 2026, the new "Sync devices" button stayed hidden from Brave and the iPhone app until they accepted the prompt (the live bundle had it). After a deploy, look at production in a fresh profile, or reload and keep your hands off the page until it has reloaded by itself (or the prompt shows, if another tab of the guide is in use). A hard reload skips the worker and shows the newest build straight away.
- **New icon art can't be counted on to reach an installed iPhone app until the app is added again.** The Home Screen icon is the one fetched when the app was added; whether iOS ever fetches it again later is not confirmed, so nothing here relies on it. On 16 Nov 2026 the new art was live at `/icons/apple-touch-icon.png`, and an iPhone's Add to Home Screen still showed the old icon. The likely cause is that the address hadn't changed, so a cached copy (Safari's, with its week of cache, or the old worker's precache) answered; which one wasn't seen. Icon URLs now change with their files (`?v=`, [core.md](core.md#the-installed-app)), which gets around Safari's cache; the old worker's precache gives way only once the new build has taken over, which is step 1 below. A reader with the app already installed:
  1. opens the guide in Safari, in a tab, and lets the new build load: hands off until the page reloads by itself, or Reload on "A new version of the guide is ready". Until then the old worker serves the old page, which names the old icon;
  2. keeps the app's progress safe first: the app's storage is its own, not Safari's ([core.md](core.md#keeping-storage)). Whether removing the app deletes it is not confirmed, so link sync in the app or use Export progress before step 3;
  3. removes the app from the Home Screen, then adds it again from that Safari tab (Share, Add to Home Screen);
  4. finds the new app linked if the Safari tab was linked to sync, since Add to Home Screen copies the tab's cookies ([core.md](core.md#syncing-devices)); that is reasoned from the cookie probe, not seen with a guide. Otherwise they import the backup in the new app.

  That the new icon then shows on an iPhone has not been seen yet.
- **Check headers on a real preview.** `vite preview` doesn't send them.

## Preview first

Nothing reaches production without being looked at on a preview deployment first. The `guide-deploy` skill (`.claude/skills/guide-deploy`) has the commands, including a header check that gets through deployment protection.

1. Push a branch. Each project whose ignore command sees a change builds a preview deployment of it, and the Vercel dashboard and the GitHub pull request link to each one.
2. On each preview that built:
   - the change itself, on desktop and phone, in light and dark ([testing.md](testing.md#in-a-browser));
   - a deep link such as `/guide/3` loads the app, and its raw HTML is the route's own file: `curl -s <preview-url>/guide/3` (through `vercel curl`, as below) has `<title>Chapter 3 is hidden · …</title>`, one `<link rel="canonical" href="https://<sub>.hundo.quest/guide/3">` and `noindex`, where `/guide/1` has its own canonical and no `noindex` and `/checklist/all/2` the shell's, with neither. `/guide/3` must answer 200 with no redirect to `/guide/3/`. If the file isn't served at the address, the catch-all still gives the shell and deep links work, so the route files are lost, not the guide;
   - a made-up hashed asset such as `/assets/nope.js` returns 404 with no long cache, and so do a made-up font, icon and `/workbox-nope.js` (`headers.sh` checks all four), while `/api/sync` and `/api/nope` are the sync API's own answers;
   - the headers: `curl -sI <preview-url>/` shows the Content-Security-Policy and the security headers;
   - `/theme-init.js` loads, and the page doesn't flash the wrong theme on reload;
   - `/robots.txt` and `/sitemap.xml` come back as `text/plain` and XML, not as the page. The `og:image` tag always names the production address (`brand.home`), which may not have the new picture yet, so fetch its path from the preview instead, `<preview-url>/assets/og-<hash>.jpg`: it should come back as a JPEG;
   - in a regular browser, the service worker registers, the guide works offline after one visit, and a newer deploy takes over at the next untouched start, or shows the update prompt to a page already in use.
3. Once every preview is right, merge to `main` with the user's go. Each project that sees a change builds production from `main`.

CI's [Lighthouse](testing.md#lighthouse) audit runs on a build served in the runner, not on a preview, so a preview's headers and its CDN are this list's to check, not Lighthouse's.

Previews sit behind Vercel's deployment protection, so a plain `curl` doesn't get through. `vercel curl`, run from a folder linked to the project, does. Anywhere else it gets a 302. The `guide-deploy` skill's `headers.sh` does this. A signed-in browser's network panel works too.

## Search Console

Set up on 19–20 Nov 2026: the `hundo.quest` Domain property is verified through a TXT record on the domain's Vercel DNS (record id `rec_c80c12583c8bd7ffabcab78e`), and all six guides' sitemaps are submitted (koholint, rdr, echoes, lordran, hallownest, pharloom). **Leave that TXT record in place**: the property's verification rests on it. Nothing in the build waits on any of this, and a new guide's sitemap is submitted when it launches (step 3). The steps, for that and for setting the property up again:

1. In [Google Search Console](https://search.google.com/search-console), add a **Domain** property for `hundo.quest` (not a URL-prefix one). A Domain property covers every subdomain, so one verification serves every guide.
2. Search Console gives a `google-site-verification=…` TXT record. Add it to `hundo.quest`'s DNS records in Vercel (team jellycat, which holds the domain): type `TXT`, name `@` (the bare domain), the value as given. Then press Verify. DNS can take a while to propagate, and Search Console says when it hasn't seen the record yet.
3. Under Sitemaps, submit each guide's sitemap:
   - `https://koholint.hundo.quest/sitemap.xml`
   - `https://rdr.hundo.quest/sitemap.xml`
   - `https://echoes.hundo.quest/sitemap.xml`
   - `https://lordran.hundo.quest/sitemap.xml`
   - `https://hallownest.hundo.quest/sitemap.xml`
   - `https://pharloom.hundo.quest/sitemap.xml`
   - and a new guide's `https://<sub>.hundo.quest/sitemap.xml`, submitted when it launches
4. With URL Inspection, inspect `https://<sub>.hundo.quest/guide/1` for each guide, and run the live test. The rendered HTML should show the guide's title, one canonical to that same address, and no `noindex`.
5. Then watch, over the following weeks:
   - **Pages, under Indexing.** The three sitemap pages should end up indexed. Hidden chapters show as "Excluded by 'noindex' tag", and the deep addresses as "Alternate page with proper canonical tag", as does `/sources` if a crawler still has it (the Sources page is gone and the address names `/guide/1`). All intended.
   - **`/`.** It shows chapter 1 by a change of address in the page, so Google is expected to treat it as a duplicate of `/guide/1`. ## The sync API

`services/sync` is its own Vercel project, `hundo-api`, on the same team, at `https://api.hundo.quest`. It is the server for sync codes ([its README](../services/sync/README.md)): one Web-standard function per route in `api/`, with Upstash Redis as the store. It is not a guide, so the rules above about every app's `vercel.json` don't reach it. It has its own `vercel.json` and its own ignore script, `services/sync/scripts/vercel-ignore.sh`, which watches the service and the root files that install its packages, but not core. `project.test.ts` holds both to what the deploy needs.

Settings in the Vercel dashboard:

- **Root Directory:** `services/sync`, with "Include files outside the Root Directory" left on, so the install runs from the workspace's lockfile.
- **Framework:** Other (`vercel.json` says `"framework": null`), **Node.js** 26.x, **production branch** `main`.
- **Domain:** `api.hundo.quest`.
- **Environment variables**, for Production and Preview: `SYNC_IP_SALT`, a long random secret (`openssl rand -hex 32`) that salts the IP hashes behind the rate limits, and the Upstash Redis REST URL and token. The code reads `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`, or Vercel KV's `KV_REST_API_URL` and `KV_REST_API_TOKEN`. With either missing, every real call answers `503 unconfigured`.
- **Reading the visit counts:** `pnpm -C services/sync stats` with `KV_REST_API_URL` and `KV_REST_API_READ_ONLY_TOKEN`, which the store's integration set for Production and Preview (seen with `vercel env ls --project hundo-api` on 17 Nov 2026). `vercel env pull --project hundo-api --environment production` from `services/sync` writes them to `.env.local`, which git ignores, with the write token beside them ([its README](../services/sync/README.md#visit-counts)).
- **The store:** an Upstash Redis database on the free plan, in Frankfurt. `vercel integration add upstash/upstash-kv --name hundo-sync -m primaryRegion=fra1` creates it (without `-m` it came up in `iad1`, and the Upstash terms have to be accepted once in a browser first). It sets `KV_REST_API_URL`, `KV_REST_API_TOKEN` and three more, for production and preview. Production and previews share it, apart by key prefix: production keys start `hs:prod:`, everything from a preview or localhost `hs:test:` and goes after a week.
- **The firewall:** three rate-limit rules on the project. Two were set up on 15 Nov 2026 from the CLI (`vercel firewall rules add …`, then `publish`): `sync api: pairing`, for paths starting `/api/pair/`, 30 requests per 600 s per address; and `sync api: calls`, for paths starting `/api/`, 120 per 60 s per address. The third, `sync api: counts` (`rule_sync_api_counts_DApaa5`), for paths starting `/api/count`, 10 per 60 s per address, was published on 17 Nov 2026, to bound the refused visit counts ([the README](../services/sync/README.md#visit-counts)). The live configuration that day (`vercel api /v1/security/firewall/config/active?projectId=…`) showed all three active with the `rate_limit` action. All count by IP with a fixed window, which is all the team's Pro plan offers besides JA4 (the docs read that day: 40 rules a project, windows of 10 s to 10 min, the first 1,000,000 allowed requests a month included, then usage-based by region, whose unit price wasn't found). A request the rule turns away never reaches the function, so costs no store command. The first two were published in log mode and switched to the 429 (`rate_limit`) action the same day, after the walk's traffic stayed far under them (its busiest minute was about 22 calls to `/api/` against 120). `vercel firewall rules edit <name> --rate-limit-action rate_limit` alone answered "No changes detected"; giving the whole setting with it (`--action rate_limit --rate-limit-keys ip --rate-limit-algo fixed_window --rate-limit-window <s> --rate-limit-requests <n> --rate-limit-action rate_limit`) staged the change, and the live configuration (`vercel api /v1/security/firewall/config/active?projectId=…`, the rule's `action.mitigate.rateLimit.action`) is what shows the mode, since `rules list` prints the same "Rate Limit (30/600s)" for either. The firewall counted, for `/api/*` calls that came through a guide's rewrite, the address of the machine that made them (`vercel firewall traffic list` and `traffic inspect ip <address>`; the other addresses in the list asked only for `/` and `/favicon.png`), so the limit counts readers apart, not edge nodes. A client over a limit gets a 429, which the guide shows as sync "paused for now" and retries later, with progress kept on the device.
- **Function Region:** Frankfurt (`fra1`), to sit next to the store, in the project's settings. The default is `iad1`. `regions` in `vercel.json` did not move the functions off `iad1` on the first preview, so the file doesn't carry one.
- **The repository link:** connect it only once `services/sync` is on `main` (see Pitfalls).

Creating the project, attaching the domain and creating the store each need the user's go, like any new project. The service can't stop a flood of requests from using the store's commands (each request costs at least one), so a rate-limit rule in the project's firewall is the guard it lacks ([its README](../services/sync/README.md#known-limits-and-what-isnt-checked-yet)).

The service shipped first and the guides' side after it: a guide's preview syncs through its `/api` rewrite to `api.hundo.quest`, which has to be live. The first guide preview showed that the API gets its own host behind the rewrite and no `x-forwarded-host` that names the guide's (every call was a `403 origin`, whatever `Origin` said), which is why the API takes who is calling from `Origin` alone ([its README](../services/sync/README.md#who-may-call)). What a preview of a guide has to show: link two browsers by code on the preview (its calls land in the `test` namespace), with `Cookie`, `Set-Cookie` and `Origin` passing through. They did on Koholint's first preview: `hundo_sync` came back host-only with `Path=/api; Secure; HttpOnly; SameSite=Lax`, `hundo_link` with `Path=/`, and two jars paired and synced. The visitor's address reached the API in `x-real-ip` and `x-forwarded-for`, as the runtime logs showed (`vercel logs -d <deployment> --json`; a temporary `console.log` of those headers, test namespace only, was added to read it and removed again). A preview of the service sits behind deployment protection, so check it with `vercel curl <path> --deployment <url> --scope jellycat -- <curl options>` from a folder linked to the project, calling it with its own address as the `Origin` (that lands in the `test` namespace and the real store). What it should do: a pairing (`pair/start`, then `pair/claim` from a second cookie jar, then `sync` from both) answers as [the README](../services/sync/README.md) says, `GET /api/sync` is `405`, an unknown path is the platform's `404` and not HTML, a POST without cookies is `401 unlinked` with its cookies cleared, and a foreign `Origin` is `403`. The build log has no TypeScript errors.

## A new project

For a new guide, after its folder passes `pnpm check` ([adding-a-guide.md](adding-a-guide.md)), and with the user's go:

1. Have the API know the guide's `brand.id` first: production's `GUIDES` has to list it before the guide's previews can sync or count ([below](#the-api-knows-the-guide-first)).
2. On the team jellycat, add the project without connecting the repository yet (step 8 connects it): `hundo-lordran` was created through the API, with a body file holding `name`, `framework` (`vite`), `rootDirectory`, `buildCommand`, `installCommand` and `outputDirectory` as `hundo-echoes` has them: `vercel api /v11/projects --scope jellycat -X POST --input <body.json> --raw > <file>` (write the answer to a file and pick fields with `jq`, never print it). The dashboard's Add New flow may import the repository; if it does, disconnect it (`vercel git disconnect`) until step 8.
3. Name it after the app's package, `hundo-<sub>`.
4. Set the Root Directory to `apps/<name>`. Leave "Include files outside the Root Directory" on. Vercel picks up the framework, install, build and output from the app's `vercel.json`.
5. Set the Node.js version to 26.x, the production branch to `main` and the preview toolbar off: the environment variable `VERCEL_PREVIEW_FEEDBACK_ENABLED` = `0`, type `plain`, target `preview` only (the dashboard's Environment Variables, or the API's create call, `POST /v10/projects/hundo-<sub>/env` on the team jellycat, with the body `{"key":"VERCEL_PREVIEW_FEEDBACK_ENABLED","value":"0","type":"plain","target":["preview"]}`). Without it each of the guide's previews logs a CSP error for the toolbar's script ([Pitfalls](#pitfalls)). Read it back with `vercel api /v10/projects/hundo-<sub>/env --scope jellycat --raw | jq -c '.envs[] | select(.key=="VERCEL_PREVIEW_FEEDBACK_ENABLED") | {type,target,value}'`, which should print `{"type":"plain","target":["preview"],"value":"0"}`.
6. **No custom domain yet.** Leave `<sub>.hundo.quest` off the project until launch (step 9): on a project with no deployments, the first deployment went to production each of the three times it was tried (step 8), and each time it took the guide's domain. Its `brand.home` is already set in `brand.ts`.
7. Run `pnpm lighthouse <name>` at the root before asking for the push ([testing.md](testing.md#lighthouse)): CI audits the guide on its first pull request, against limits set from the guides that do worst. A failure is fixed in the guide, never by loosening a threshold, which is the user's call.
8. **The first deployment has landed on production, so check it there, without the domain.** On a project with no deployments, the first deployment went to production three times on 17 Nov 2026 (`hundo-lordran`): from `vercel deploy`, from `vercel deploy --target preview`, and from a Git push of the pull request's branch with the production branch set to `main`. The next push of the same branch, with that first deployment in place, built a preview (target `preview`, the first one still the only production). So connect the project to `salty-max/hundo` (`vercel git connect`, production branch `main`) once the guide's pull request is open, and push a commit whose last change touches the app, core, `scripts` or the root workspace files (a new project has no earlier deployment, so the ignore step sees only that commit, as above). After any deployment, read its target and aliases back before anything else (`vercel api /v13/deployments/<id> --scope jellycat --raw | jq '{target, alias}'`), and the project's domains (`vercel api /v9/projects/<project>/domains --scope jellycat --raw | jq -r '.domains[].name'`). The first one has been production: the project's domains must then be `.vercel.app` names only. Any later one before launch that says `production`, or a `hundo.quest` name among the project's domains before launch: stop and tell the user. Read the domains from the project, not from the deployment's `alias` list, which kept `lordran.hundo.quest` after it was detached from the project (17 Nov 2026). Never run `vercel deploy`, `redeploy`, `promote` or `alias` on the project before launch. Until the merge, other branches' pushes show a failed deployment on it, because they lack the folder (see Pitfalls).

   Check that first deployment on two addresses. `<project>.vercel.app` (`hundo-lordran.vercel.app`) is open, but the sync API refuses its origin by design (`{"error":"origin"}`): it serves only `*.hundo.quest` (as production) and `hundo-…-jellycat.vercel.app` (as `test`), and the rule stays that narrow. So run headers.sh and look at the page there or on the branch's address, and check sync and the visit count on the branch's address, `<project>-git-<branch>-jellycat.vercel.app`, which sits behind deployment protection: sign in to Vercel in the browser, or send the project's bypass token as `x-vercel-protection-bypass` from a script (without `x-vercel-set-bypass-cookie` on every request, which loops POSTs in 307s), and never print the token. Its counts land in the `test` namespace (`pnpm -C services/sync stats --test`).
9. **Launch is one go from the user, covering the merge and the domain, in this order.** Before asking for it, make sure the pull request's last commit touches the app, core, `scripts` or the root workspace files: a rebase merge makes that commit `main`'s head, the project has never deployed `main`, so `VERCEL_GIT_PREVIOUS_SHA` is most likely empty on that build (inferred from Vercel's docs, as above) and the ignore step then sees only that commit. A docs-only last commit would then cancel the first production build of `main`: `vercel ls` shows a `main` deployment whose state is canceled ("The Ignored Build Step command returned exit code 0"), so check its state, not only its ref. If that happens, stop and ask the user: no CLI deploy is allowed before launch. Merge the pull request; wait for the project's production deployment of `main` (`vercel ls <project> --scope jellycat`, then its `meta.githubCommitRef` must be `main`); only then add `<sub>.hundo.quest` to the project's domains. Adding the domain earlier would most likely serve the project's current production deployment, the pull request's build, on the real address at once (Vercel's documented behaviour for a domain, not tried here). Then submit its sitemap in Search Console ([above](#search-console)). The root README's apps table row is part of the guide's own pull request ([adding-a-guide.md](adding-a-guide.md#4-wire-it-into-the-repository)), since `pnpm check` fails without it.

### The API knows the guide first

A guide's `/api` goes to production's `https://api.hundo.quest`, previews included (their calls land in the `test` namespace, [the sync API](#the-sync-api)). The API takes the guide from the `guide` a call names, and `GUIDES` in `services/sync/src/app.ts` is its list of `brand.id`s. For an id it doesn't list, probed on 17 Nov 2026 against `api.hundo.quest` from a preview's `Origin` (nothing is stored):

- `POST /api/count` and `POST /api/sync` answer `400 {"error":"guide"}`, after the origin, content type and protocol checks and before any call to the store. On a preview the visit counts then silently don't land (the guide sends them and shows nothing), and a sync round is refused, which the guide treats as a failed round to retry later.
- `POST /api/pair/claim` only counts the new link under the guide it names, and ignores an unknown one: pairing still works (from the code, not probed).

A route production doesn't have yet is a different failure, with the same cure: it answers a plain-text `404` from Vercel (`The page could not be found`), not the API's JSON `not_found` (`POST /api/nothing`, same day). The analytics previews got that on 17 Nov 2026, before `/api/count` was deployed. To see whether the deployed API knows an id, send it empty counts with an `Origin` shaped like a preview's, which stores nothing:

```bash
curl -s -X POST https://api.hundo.quest/api/count -H 'Origin: https://hundo-<sub>-git-x-jellycat.vercel.app' -H 'Content-Type: application/json' -d '{"p":1,"guide":"<brand.id>","counts":{}}'
```

`{"error":"counts"}` means the id is known, `{"error":"guide"}` that it isn't.

Two ways, and the user's go for either's merge, since a merge to `main` that touches `services/sync` deploys `hundo-api`:

1. **The id in a pull request of its own, deployed first (recommended).** One line in `GUIDES` and nothing else. `project.test.ts` takes an id ahead of its guide, so it passes its own CI. It changes nothing for anyone while no guide sends the id (sync and count only look ids up, and unlink and forget delete a few more keys that don't exist), and it deploys `hundo-api` alone: no guide's ignore command watches `services/`. The guide's previews then sync and count from their first push, and the check above confirms it first. A `brand.id` never changes, so settle it with the user before this pull request, whose line is its first use.
2. **The id with the guide.** The line goes in the guide's own pull request. Its previews show the refusals above, so the sync and count checks wait until after the merge: link two browsers on the production site, and read the count with `pnpm -C services/sync stats` ([the sync API](#the-sync-api)). The merge deploys the guide and `hundo-api` from the same commit.
