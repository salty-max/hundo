# Changing core

`packages/core` is the app: its pages, components, stores, styles, the page shell and the build config. Every guide ships it, so a core change reaches every guide's site. Every guide's Vercel project rebuilds on it, because their ignore commands watch `packages/core`.

## How core and a guide meet

- **Core reads a guide only through `virtual:guide/…`.** `guide.ts` imports `virtual:guide/config`, `Layout.tsx` and `DashboardPage.tsx` import `virtual:guide/panels`, and `main.tsx` imports `virtual:guide/theme.css`. `vite.ts` aliases `virtual:guide/` to the app's `src/guide/`, and each app's `tsconfig.json` maps the same path for the typechecker. A new file core reads this way must then exist in every guide.
- **A guide reads core only through the subpath exports** in `packages/core/package.json`: `types`, `format`, `fonts`, `guide`, `reader-text` (tests only), `progress-state`, `store/*`, `sync/*`, `components/*`, `vite`, `icons` and `app.css` (the stylesheet, which Storybook loads). To give guides something new, add an export. There's no barrel file, on purpose.
- **`config.ts` stays at the bottom of the import graph.** A guide's `config.ts`, and the helpers it imports (`run-log.ts`, `estimate.ts`), use only `@hundo/core/types` and `/format`. Core's `guide.ts` imports the config, and the stores import `guide.ts`. A config that reached for a store or a component would close the loop. Panels can use core's stores and components, because nothing in the config imports them.
- **Per-guide saved state** goes in `extra`. A guide declares its type by declaration merging on `"@hundo/core/types"`'s `Register`, as `run-log.ts` and `estimate.ts` do. `GuideConfig.state.extra` then reads and initialises it.

## Saved progress

Readers' progress lives in their browser, so a careless change can wipe it.

- The keys are `<storagePrefix>.v1` for progress (`progress-state.ts`), `<storagePrefix>.theme` for the theme (`store/theme.ts`), `<storagePrefix>.sync` for a synced device's ledger (`sync/local.ts`), `<storagePrefix>.awake` for Keep screen on (`store/awake.ts`), `<storagePrefix>.place` for the last place read, reopened at launch (`store/place.ts`), `<storagePrefix>.persist` for when the guide last asked to keep its storage (`persistence.ts`, below), `<storagePrefix>.counts` for Count my visits turned off (`counts.ts`, below), `<storagePrefix>.build` for the leanings of the reader's build and `<storagePrefix>.build-asked` for whether the guide has asked for one (`store/build.ts`, [Builds](#builds)). `theme-init.js` reads the theme key before the app loads. Don't change how any key is built. Each guide's `guide.test.ts` pins all nine full keys, and the name of the cookie hundo.quest reads, `hundo_p_<brand.id>` (below).
- `boot.ts` runs before any store reads storage. It redirects the old hash routes (`#guide/3`). For a guide that moved address (`brand.home` and `brand.movedFrom`), it also hands each reader's progress over from the old address to the new one, through the URL fragment. No guide lists `movedFrom` today, so the hand-off stays inert until a guide moves again. `boot.test.ts` covers the handover, and [deploying.md](deploying.md#pitfalls) says when to use it. `main.tsx` imports it first, and renders nothing while it's leaving for the new address. Keep that order.
- Saves and backups use one format, `{ version: 3, guide, checks, ceiling, spoilers, chapter, extra }`. `validateState` reads every save on load and every imported backup, and quietly drops checks for ids the data doesn't have.
- To change the format: bump `version` inside the saved object (not the key's `.v1`, which stays forever), keep reading every older version, and write only the new one. Then extend `progress-state.test.ts` and each guide's legacy cases in `guide.test.ts`, the ones that load real older saves. The three guides still read their saves from before the shared format through `config.state.legacy`.

## Keeping storage

By default a browser may clear a site's storage on its own, and progress with it. `persistence.ts` asks it not to with `navigator.storage.persist()`, on the reader's first tick of a visit in that tab (never on load, and never for a tick another tab saved), unless storage is persistent already or the guide asked in the last 30 days. An installed app asks once more if the last ask came from a tab. When and where it last asked is kept under `<storagePrefix>.persist`, as `<ms> tab` or `<ms> app`. It's written before any wait, so two tabs that each tick, or a new visit while a Firefox prompt is still open, don't ask again. Losing or renaming that key would only mean asking again early, but for a Firefox reader who blocked the prompt that's a prompt again, so it is pinned with the other keys and doesn't change. The dashboard's Progress backup panel adds a line when `persisted()` says no, pointing to Export progress and, outside an installed app, to the home screen with the backup imported there. `persistence.test.ts` covers the rules and `App.test.tsx` the tick and the dashboard line.

What each browser does with the request (checked 2026-11-15):

- **Chrome and other Chromium browsers** decide silently: granted if the site looks important to the reader (engagement, installed or bookmarked, notifications allowed), otherwise refused, and asking again later is fine ([web.dev](https://web.dev/articles/persistent-storage)). Without it, storage can be evicted when space runs low ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- **Firefox** asks the reader with a permission prompt, with no click needed first. "Allow" is remembered. "Block" lasts only a while unless they tick "remember", which is why the guide waits 30 days between asks. A private window gets no prompt and a refusal (`PermissionUI.sys.mjs` and `dom/quota/StorageManager.cpp` in [Firefox's source](https://github.com/mozilla-firefox/firefox)).
- **Safari** (17 and later) decides silently, "based on heuristics like whether the website is opened as a Home Screen Web App" ([WebKit, 2023](https://webkit.org/blog/14403/updates-to-storage-policy/)). Safari also deletes a site's script-written storage, localStorage included, after seven days of Safari use without the reader interacting with it. Home-screen web apps keep their own count and aren't expected to lose their data ([WebKit, 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). The 2023 post says a persistent origin "might be excluded" from eviction, the seven-day kind included. On an iPhone (iOS 18.7, Koholint's live build, 2026-11-15), Safari didn't grant the request in a tab: after a tick, which is when the guide asks, the dashboard still showed the line. Added to the home screen, the guide opened with nothing ticked: the app didn't start with the tab's progress. The line showed in the app on opening too, from `persisted()`, before anything was ticked there. After a tick in the app, which is when the guide asks, the line was gone: the app's storage was persistent once the guide had asked. So on that iPhone the home screen is where the guide's storage became persistent, and the advice the line gives in a tab, to add the guide to the home screen and import the backup there, holds.

## Syncing devices

`src/sync/` keeps one guide's progress the same on a reader's devices, through the API in `services/sync` ([its README](../services/sync/README.md)). Device storage stays the truth and sync only catches up; nothing here runs, or costs a request, until a device is linked.

- **Pairing:** a device shows a six-digit code and another types it (`SyncScreen.tsx`, opened by `{ kind: "sync" }`; `sync/pairing.ts` holds its calls). No account. The server sets a `hundo_sync` cookie that script can't read and a `hundo_link` one it can, and the guide reads only the second, to know it is linked without a request. On hundo.quest the link covers every guide in a browser. Installed phone apps keep their own storage and cookies, so each installed guide takes a code of its own (below).
- **What `hundo_link` and `<prefix>.sync` mean together:** neither, nothing runs. The cookie only, this guide joins the group: it pulls first, then sends what it adds, so linking merges and never replaces (`seed` in `sync/fields.ts` holds the rules). The ledger only, the link is gone (unlinked in another guide, or expired): the ledger is dropped and progress stays. A cookie that names another group than the ledger's means the device moved (it typed a code from a device in one): the old ledger goes and it joins afresh, as for a first link, since an untick stamped in the old group means nothing in the new one.
- **The ledger is the merge model.** `sync/ledger.ts` is byte for byte `services/sync/src/ledger.ts` (`ledger.test.ts` holds them equal; change both together): each key (`c:<rowId>`, `ceiling`, `chapter`, `spoilers`, `x:<path>`) has a stamp, and the later one wins. `sync/fields.ts` flattens a state into keys and lays them back over it. A row id has to be a valid key (`ledger.test.ts` checks every row), and a guide's `extra` goes by leaf: keys of letters, digits, `_` and `-`, at most 60 leaves of at most 256 bytes. A leaf that doesn't fit is left out of sync, not sent.
- **Stamping happens in `store/progress.ts`'s `commit`**, after the save, through `recordLocalChange`, so a change made here is stamped and marked to send. `applySynced` (what sync pulled) and `reloadFromStorage` (what another tab saved) don't stamp, or a pull would be sent straight back. `replaceAll` does, which is why an import replaces progress on every linked device, and the settings say so. The progress is written before the ledger.
- **`sync/cycle.ts` is one round**, under `navigator.locks` so two tabs take turns; `sync/engine.ts`, started by `useSync()` in `App.tsx`, decides when: on opening, 2 seconds after a change (never more than 15 after the first unsent one), as the page hides (a push with `keepalive`), on coming back after 10 seconds or more (`visibilitychange`, and `focus` and a bfcache `pageshow` where those come instead or as well, since an installed iPhone app doesn't always fire the same one), while showing every 20 seconds, backing off by half again each poll that finds nothing (and nothing was changed here) up to 2 minutes and quick again after a change on either side (`pulled` in a round's outcome says the group had something new), never while hidden, and when the browser is back online. After a failure it backs off from 5 seconds to 5 minutes and doesn't poll on top. What polling costs: a poll with nothing to send asks the server whether the guide's data has changed (it sends the revision it last saw), and when it hasn't the answer costs two store commands and nothing is pulled or written on either side. A poll that finds a change, or any full sync, costs six, and eight when the API refreshes the device's last-seen, which only full syncs do, so eight in practice; a push costs ten or eleven, twelve or thirteen with the refresh. The client makes a poll a full sync every ten minutes, and when its daily touch is due. So a guide left open and untouched asks about 33 times an hour, some 100 commands (some 230 before revisions). Against the free plan's 500,000 commands a month (shared by every reader of all three guides): two devices with a guide open 8 hours a day and untouched come to about 50,000, and a pair in steady use all that time, with a tick every three minutes on one or the other, to about 200,000 (an estimate from those rates: some 80 quiet polls, 10 polls that find a change and 10 pushes an hour for each device; some 430,000 to 480,000 before revisions). Because quiet polls leave a device's last-seen alone, the device list can show one that is polling as seen up to about twelve minutes ago, so the Sync screen says "Seen in the last 15 minutes" for any fresher than that. When the quota runs out the API answers 503, and the guides show sync as paused and go on working on their own. The firewall's 120 requests a minute for an address is far off with three devices (9 a minute at the quick pace). Only the server's own `401 unlinked` unlinks a device; a network error, a full store (413), one that is busy or not set up (503) or a limit (429) leaves progress and the ledger as they were.
- **A guide's chapter and ceiling** are held to its own chapter count and never reset to 1, a row this build doesn't know stays in the ledger without being applied, and `viewFrom` moves the open chapter back to the ceiling under spoiler protection as a view, never a stamped change.
- **The theme is deliberately per device.** Devices want different themes ("system" already follows each one's own setting), and `theme-init.js` applies `<prefix>.theme` before first paint, before any network answer exists. Progress, spoiler settings, ceiling and chapter do sync. The build pick is per device too, for its own reasons ([Builds](#builds)).
- **Tests:** `sync/cycle.test.ts` runs two browsers (their own storage, cookies and addresses, in `test/sync-world.ts`) against the real API handler on an in-memory store, so what the guide sends is what the API accepts. `engine.test.ts` (fake timers), `fields.test.ts`, `local.test.ts`, `SyncScreen.test.tsx` and the stamping cases in `store/progress.test.ts` cover the rest, and each guide's `guide.test.ts` pins its `extra` as keys.
- **The two devices of a pair link a few seconds apart, so each runs follow-up rounds.** The one that types the code joins at once, to a group that has nothing yet; the one that showed it learns of the link from its next status look (every 3 seconds) and only then pushes what it has. So `syncAfterLinking()` in `sync/engine.ts` runs a round at once and again after about 3, 8 and 15 seconds, on both sides (the quiet poll makes each cost two store commands when nothing has arrived), and the new device's screen fills without a reload. Before this, the typing device waited for its next poll: every 5 minutes before the polling change, every 20 to 120 seconds after it. `cycle.test.ts` has the sequence with the real handler.
- **Another device can be removed from the group** (`removeDevice`, the Remove button on every other device's row, behind a confirm; `/api/remove` on the server, which checks the target's own record). The device finds out on its next call (`401 unlinked`) and keeps its own progress; nothing is deleted from the others. The list's ids come from an up-to-date server; an older one's list has none, so no button shows. A device the group hasn't heard from for 60 days is removed by itself the next time its group is read (the quiet poll doesn't read it), records and all: a lost phone that wakes up is unlinked and has to be linked again, and a reinstalled app's old entry goes by hand or after 60 days. A stolen cookie can remove every other device (the README's known limits say so).
- **The title bar's status button always opens the Sync screen** (`SaveStatus` in `TopBar.tsx`), linked or not, with "Open sync devices" ending its name in every state ("Progress saved. Open sync devices", "Progress saved. Synced. Open sync devices", "Storage unavailable. Open sync devices"). It once opened the settings for a device that wasn't linked, so one button led to two places depending on something the reader couldn't see, and on 16 Nov 2026 the user reported the Red Dead app opening Sync where the other two guides opened the settings. When the browser won't keep the progress, the Sync screen's first screen starts with the same paragraph the settings carry (`StorageWarning.tsx`, one component, so the words stay one) and an Export progress button under it (the settings have theirs below), and no longer says the progress is saved on the device. In both screens that paragraph is what the dialog's `aria-describedby` points to (seen in all three guides, phone and desktop, light and dark, on 16 Nov 2026), which a screen reader reads on opening. A dialog has one description and only one may be mounted at a time (Base UI keeps a single id and a description that unmounts clears it), so the Sync screen's own intro steps aside as a plain paragraph while storage is unavailable (`ScreenIntro`). Both Export buttons say "Progress backup exported." in a line inside the dialog, because the page's own announcement is behind the modal (the same day its `#status` had an `aria-hidden` or `inert` ancestor while a dialog was open, in all three guides). Neither the description nor that line was tried with a real screen reader. Not checked: whether linking and syncing work while storage is unavailable. Guide settings is reached from the chapters menu's "Change settings" (the rail beside the page from 801px) and the Progress page's "Import progress".
- **A device that shows a code links only while its Sync screen is open.** Showing a code again links it if another device typed one meanwhile.
- **A reader's guide gets a new build without a nag mid-session** (`registerType: "prompt"`, [deploying.md](deploying.md#pitfalls); `sw-updates.ts`, wired in `ToastHost`). The browser looks for a new worker only when the page loads, and an installed app can stay open for days, so the page looks itself: when it comes back to the screen and on a timer, at most once an hour. A build that is waiting while the guide is only just starting (nothing pressed, typed or scrolled in the first 20 seconds, no dialog open, no other tab of the guide in use) takes over at once: the worker skips waiting and the page reloads, after any sync round under way. A page no worker controls (a hard reload) already runs the newest build, so it neither takes over nor asks. A build found later still waits for "Reload" on "A new version of the guide is ready", so a reload never lands mid-checklist. Another tab counts as in use when it holds the shared Web Lock `hundo-in-use`, which a page takes on the reader's first action: taking over reloads every open tab of the guide, and one being used mustn't reload under the reader. The first real link on 15 Nov 2026 is why this exists: Brave and the installed iPhone app, open before the deploy, showed no "Sync devices" button in the settings until "Reload" was pressed. Whether an installed iPhone app reopened after a deploy comes back on the new build without the toast is not verified on a phone.
- **On an iPhone, each guide on the Home Screen is a device of its own.** WebKit says a Home Screen app's storage is separate from Safari's once it is added, and the probe saw it copy Safari's cookies once, at that moment. On 15 Nov 2026 the user linked the Koholint app, and the Red Dead app, an app of its own on the same iPhone, wasn't linked, although `rdr.hundo.quest` in Brave was (one link covers every guide in a *browser*). That fits one cookie jar per app. Whether the Red Dead app had taken the update then isn't known, and wouldn't change it, since the link's cookies never reached it. So the Sync screen says it on an Apple device, on the Off and the Linked screens (it says a guide added after linking in Safari should come up linked only to a reader in Safari: whose cookies an app added from another iPhone browser copies is unverified), and an installed app's label carries its guide (`deviceLabel`: "Safari · iPhone · Koholint app", the guide's `brand.shortName`; a label is what the server lists as the device, 40 characters at most, and a guide's name isn't personal data). The label is sent when a device links, and the server changes a device's label only when it is made or moves to another group, so a device linked earlier keeps "… · installed app" until it is unlinked and linked again. The guide's name goes in only on Apple devices: an installed Chromium app on desktop or Android normally shares its browser's cookies (general knowledge, not tried here), so it is one device with the tab, whichever guide linked it, and keeps "· installed app". Which guides a device has synced isn't shown: the server keeps one "last seen" per device, not per guide, and showing it would need a record per device and guide, deleted along with the rest on unlink, forget and expiry, an API change and a deploy. The label tells the same story for the price of none of that. An app added *after* a link was made in Safari is the exception, most likely: Add to Home Screen copies the tab's cookies, and the probe saw an `HttpOnly` one copied, so the app would carry the tab's own device cookie (`hundo_sync`) and the server would count the two as one device, with one row in the list under the tab's label, and unlinking either would unlink both. That is reasoned from the probe and the API's cookies, not seen on a phone; linking in Safari, adding the guide, and counting the devices on both Sync screens would settle it.
- **Checked on real devices (15 Nov 2026, production):** Brave on a Mac and the installed Koholint app on an iPhone linked by a typed code and synced both ways, an untick included, and `rdr.hundo.quest` in the same Brave showed "Progress saved · Synced" with no code of its own. The production log showed `pair/start`, `pair/claim` and the syncs as 200. The same day, with the new build, the Red Dead app on that iPhone took a code of its own (the Mac in Brave showed it linked: three devices, "Chrome · Mac", "Safari · iPhone · installed app" for the Koholint app and "Safari · iPhone · RDR app"), a tick made in the app reached the Mac after a reload, and one made on the Mac reached the app after it was swiped away and reopened. The Echoes app wasn't on that iPhone, so it wasn't tried.
- **The chapter is a reading position, and a visit stamps it.** A device sitting on a hidden chapter's page that a pull then reveals records that visit as its own change, and so takes the chapter back from the device that moved on.

## Visit counts

`counts.ts` counts visits for the questions the guides are run by: which guides and chapters get used, how far readers get, and how much reading happens in the installed app. It counts events, never people: no cookie, no id, nothing on the device but the off switch. The README's "Privacy" section tells readers exactly what is sent and kept, and changes with any change here, as does the switch's note in Guide settings (`screens.tsx`). The legal footing is the CNIL's audience-measurement exemption from consent ([CNIL, mesure d'audience](https://www.cnil.fr/fr/cookies-et-autres-traceurs/regles/cookies-solutions-pour-les-outils-de-mesure-daudience)): measurement for the publisher alone, anonymous statistics only, nothing crossed with other data (so a visit's counts never say whether the device is linked; the server's link count and group snapshot are sync's own figures, made on the server and kept apart from them), no tracking across sites, readers told, data kept 25 months at most. Keep any new field inside those, or the guides would need a consent banner.

- **The fields:** `v:app` or `v:tab` once a page load (and again after 30 minutes in the background), from `installed()`; `p:guide/<n>`, `p:checklist`, `p:questlines`, `p:dashboard` for each page shown (`pageOf`: a row, section, line or filter isn't a new page, and a hidden chapter isn't counted); `s:<n>` and `f:<n>` when the reader's own change takes chapter n from no row checked to some, or to all (a tap or a bulk check; not what sync pulled or another tab saved, which run inside `notATick`, nor an import, which runs inside `uncounted`). Each start and finish counts once a page load, so undo and redo count once. A synced device that hasn't pulled yet judges against its own view, so two devices can each count the same start: the numbers are indicative. Only chapter numbers leave the device. The API refuses any other field (`COUNT_FIELD` in `services/sync/src/app.ts`), except `p:sources`, which it still takes from builds older than the Sources page's removal (17 Nov 2026), so their counts aren't refused while they wait to update. One field the API doesn't know makes it refuse the whole POST, so a new field ships in the API before any guide sends it, as `p:questlines` did.
- **Sending:** the fields wait in memory and go as one POST to `/api/count` when the page goes to the background (`visibilitychange`, and `pagehide`), or at once when a POST is full (12 fields, or 50 of one). `fetch` with `keepalive` and `credentials: "omit"`: the sync cookie names the device, and a count must not carry it, which is also why it isn't `sendBeacon` (which always sends cookies). A failure is dropped without a word. Nothing goes out while the page loads.
- **Off:** Count my visits in Guide settings writes `<storagePrefix>.counts` = `"off"` on save (per device, not synced, not in backups), and drops what was waiting. A browser sending Global Privacy Control or Do Not Track is never counted, and the switch shows off and disabled there with a note saying why.
- **The server side** ([services/sync/README.md](../services/sync/README.md#visit-counts)) adds a POST's counts to the guide's totals for the day, keeps them 25 months, and stops writing for the month at a budget of store commands, to leave sync its quota (what still costs a command after that is in its README). It also counts each new link (`pair`, from the `guide` that `pair/claim` sends only when `allowed()`, so a reader who isn't counted isn't counted there either). `pnpm -C services/sync stats` reads it all.
- **Tests:** `counts.test.tsx` covers the fields, what counts and what doesn't, the off switch, GPC and DNT, and the sending; the API's own tests cover what it accepts and stores. The Settings stories (`Dialog.stories.tsx`) show the switch, turning it off, and a browser that sends GPC.

## hundo.quest's summary

hundo.quest shows a returning reader each guide they've started, with its figure and their chapter. The landing page can't read a guide's storage, so `summary.ts` keeps a cookie for it on every hundo.quest host, `hundo_p_<brand.id>` (`SUMMARY_COOKIE`), holding `1.<percent>.<chapter>`: the format, `overall(checks).percent` (the Progress page's own figure, never a copy of its rule) and `data.chapter`, the chapter last visited. With nothing checked there is no cookie.

- **The API sets it, never this script.** Safari has kept a cookie set by page script for as little as a week, and one set by a response as long as it asks ([services/sync/README.md](../services/sync/README.md#a-guides-summary) has what was checked, and what wasn't). So `summary.ts` only reads `document.cookie`, and asks `/api/summary` through `call()` (`sync/api.ts`, `credentials: "same-origin"`, which a browser needs to keep the answer's cookie). `summary.test.ts` fails if anything in core's code writes a cookie.
- **When it calls:** `startSummary()` runs once from `main.tsx` (not while `boot.ts` is leaving for a new address). It looks five seconds after the guide opens, and five seconds after the last change to the checks or the chapter, whatever made it (a tick, a backup, sync, another tab): one call for a run of changes, and for the opening look and sync's first pull. A call still waiting goes at once, with `keepalive`, when the page is hidden. It compares with the cookie when it goes, so a change another tab has already sent isn't sent twice, and it never sends the same text twice in a page load, so a failure (offline, or a preview whose API lacks the route) costs one call until something changes. A linked device (the `hundo_link` cookie, `readHint()`) differs in two ways, below.
- **What it doesn't do:** Count my visits off, Global Privacy Control and Do Not Track don't stop it. They are promises about counting, and this counts nothing: it is a feature the reader sees, and the server keeps none of it for a reader who doesn't sync. A switch of its own would be a new key.
- **On a synced device** the call brings `hundo_sync`, as every call to `/api` does, and the API also keeps the summary for the device's group, which hundo.quest reads in the group's other browsers (`/api/summaries`, [services/sync/README.md](../services/sync/README.md#a-guides-summary), and home's side in [home/README.md](../home/README.md)). hundo.quest shows the higher of the group's copy and its own cookie, and takes the group's "nothing checked" as a reset ([home/README.md](../home/README.md) has the cases that shows wrong), so what a linked device sends must be the group's progress, not its own from before it caught up: until this page load's sync has finished a round (`useSyncStatus`'s `lastSync`), `sendSummary` sends nothing, and a waiting call is dropped (an app just added to the Home Screen starts with Safari's cookies and none of the progress, and would otherwise tell the group "nothing checked"). Once that round has finished it sends once, whatever the cookie says (`owed`), with the same five-second wait, so a device whose cookie is already in step still tells the group, after a deploy or a link that changed nothing. Then only changes, as unlinked. An unlink starts it over, so a group it links to next in the same visit waits for its own first round. It costs a linked device one call a page load more at most, two store commands. On a device that stays offline or whose sync keeps failing, the cookie doesn't move on that visit.
- **Where it doesn't reach:** an installed iPhone or iPad app keeps its own cookies, apart from Safari's, so without sync hundo.quest in Safari doesn't see its progress; linked, the group's copy carries it. After an update changes a guide's totals, the figure stays the old one until the reader opens that guide again.
- **How long it lasts:** 400 days from the last change it carried (180 in Brave), since a call goes out only when the cookie says something else; on a linked device, from the last visit, since the call after the first sync sets it again. A reader who opens a guide for months without a change can find its band blank on hundo.quest until the next change or the next visit after the cookie has gone.
- **Previews and localhost:** the cookie is host-only there, so a guide's preview can't show it on home's preview. On localhost it works end to end, since cookies ignore ports. Tried on 20 Nov 2026 with the `sync-api` server, Koholint's dev server sending `/api` to it, and `home`'s dev server: 40 ticks made one call, the cookie came back `1.9.1` (host-only, readable, a week in the `test` namespace), Koholint's Progress page said 9%, and home's band said "9% complete · Chapter 1"; a reader with progress and no cookie got it from the look after opening, and the next visit, in step, made no call.
- **Its footing:** it isn't measurement, so the visit counts' footing (the CNIL's audience-measurement exemption) doesn't cover it. It keeps the reader's own figure for a page they see; whether that needs asking first wasn't looked into.

## Questlines

Chained side quests (an NPC's arc, a trading sequence, a Stranger's task) are lines of existing rows, listed in each guide's `data/questlines.ts` and drawn on the Questlines page (`pages/QuestlinesPage.tsx`, `/questlines/<line>`), the fourth item in the navigation. Progress stays per row: ticking a step there ticks the row, and nothing new is saved. `questlines.ts` holds the rules, and `questlines.test.tsx` checks them in every guide:

- **A line exists only once its first step's chapter is revealed.** Until then it isn't listed or counted, and the page's callout says only that more appear as chapters are revealed.
- **Only revealed steps show.** A line keeps to route order (`data.test.ts`), so those are always its first steps, and no count says how many are left.
- **No line says it is complete while a chapter is hidden.** Every card ends with the same "Anything past chapter N stays hidden.", and a line whose revealed steps are ticked is "Done through chapter N". Saying "Complete" of only the lines that end would tell which go on.
- **The next step is the first unticked one after the last ticked one** (or the first unticked one, when the last revealed step is ticked). An earlier unticked step isn't called skipped: some are conditional, and one stray tick shouldn't brand the steps before it. A line is done only with every revealed step ticked.
- **A row's chip** (`LineChip.tsx`), beside a row in either layout, says "Name · step k" and links to the line's card, once the line has two revealed steps or more (counting hidden ones would tell that a line goes on). It never says "of n": every step up to the row is revealed, the later ones may not be.
- **A small link's tap area.** A link that is alone in its cell (`rowLinkClasses`: Jump to, "Chapter 3" on the checklist, "Ch 05" on the questlines page) reaches 8px above and below its words and 2px to each side, with negative margins, and takes no room: nothing else a finger could mean is within 8px of it. A link that can wrap onto a line of its own under a box, or sit above or below another link (`stackedLinkClasses`, the map link; `lineChip`, the questline and choice chips) has no reach: its box is its tap area, 24px tall at least, in the row's flow. A reach there ran into its neighbours (the chip's 8px into a compact row's 26px checkbox, 6px past the 2px between lines; the map link and the chip into each other in a route row's column of tags), which axe's `target-size` counts as the box being covered (WCAG 2.2: 24px, or room around it) and Lighthouse's accessibility score drops for it. A chip in a compact list or in the column is a block with `min-h-6` and its words centred (`content-center`); in prose it stays inline, as a link in a sentence is, and only its padding is taller than its words. axe's rule leaves out a link that sits inline in a sentence, so the prose chip and the prose map link are held by `LineChip.stories.tsx`'s own measurement (no two tap areas overlap, and the paragraph keeps its line pitch), which runs in every look with `target-size` on for the rest.
- A line's id is in its address, so it stays once live. Its count field is `p:questlines`, never the id.

## One-way choices

A guide's `config.choices` (its `data/choices.ts`, [chapter-data.md](chapter-data.md#one-way-choices)) lists decisions a playthrough can't take every way of. Each has a row recommended for this playthrough and, in later chapters, a row for each other way. Every way is an ordinary row, ticked and counted like any other, so nothing here changes a count, a saved key or a row id. What core adds is how a choice reads (decided 19 Nov 2026, after an inventory of every guide found no choice with two ways one save could both reach):

- **The block** (`ChoiceBlock.tsx`) takes the recommended row's place, in an article's prose or compact list (`ArticleRoute`) and in a checklist group (`RouteGroup`, so on the Checklist page and in Red Dead's route). In the article it's an inset on the page's colour, and in a group a band between the rules. It holds a fork, "One-way choice", the name and a state ("Decide once", then "Done"), then the why, then "Recommended this playthrough" over the row, drawn as its list draws any row. Under "Later playthrough" come the other ways, each with its title linking to its place, its playthrough and its chapter's number, and a tick once it's done there. That list carries `data-nosnippet` ([Search engines](#search-engines-and-link-previews)). Only the recommended row has a box: a later way is ticked in its own chapter, where it carries a link back to the choice (`ChoiceChip`). The choice's chapter is earlier, so it's always revealed when the later one is.
- **The warning.** Core gives the recommended row the `one-way` tag, as it gives a missable's row `missable`. "Don't miss before moving on" lists it with the why until it's ticked (`missablesLeft`, `missableWhy`), and a guide that flags no missable keeps its reassurance in every chapter with nothing to list, and so does Next up when it's next, with the amber One-way tag beside the why (`TickItem`'s `tag`). The Questlines page shows the tag and the why on its step, as a missable step shows its condition. Outside its block the row carries the tag, and inside the block it doesn't, since the block says it. The Checklist page and a checklist route offer a "One-way" chip once a guide has a choice (`hasChoices`), and the kept filters accept it (`store/place.ts`). There is no confirm on ticking: the tick comes after the choice was made in the game. Nor is there a notice a chapter ahead, which would tell a reader that a hidden chapter holds a choice.
- **Accessibility.** The block is Base UI's `Fieldset`: a `<fieldset>` named by its legend ("One-way choice Frampt or Kaathe"), with the why as its description, so a screen reader hears the group, the why, then the recommended row's checkbox. It is not a radio group: there is one box, a radio can't go back to "not yet", and its arrow keys would move a tick along with the focus. Nor is it Base UI's `CheckboxGroup`: a box inside one takes its checked state from the group by its `value`, or its `name` when it has no value (`CheckboxRoot`), which would set aside the store's tick that each row's `CheckBox` reads, and the row boxes need their `name` (Loaded on use).
- **Counting** is the rows', unchanged: the recommended row counts in this playthrough and each later way in its own chapter.
- `ChoiceBlock.test.tsx` mocks a choice in every guide (the block in both layouts, its name and description, the later way's link and tick, the link back, "Don't miss" and Next up). `data.test.ts` holds the data rules. The ChoiceBlock stories run under axe in every palette and theme.

## Builds

A guide whose game is played by build (Lordran) can point a reader toward theirs without changing what 100% means: a build is a lens over the checklist, never a second one (decided 21 Nov 2026; recommendations and steps added the same day, after the reader asked for them; woven into the rows as notes on 22 Nov 2026, after the chips and lines under a row read as an annex). The guide's `config.builds` holds its leanings, its named builds (with how guides start each), its picks, its steps and its notes ([chapter-data.md](chapter-data.md#builds)); a guide without it renders nothing of builds and looks as it always has (`builds.test.tsx` holds that in every guide without builds); its rows never read the pick.

- **The pick** is a set of leaning ids. `store/build.ts` keeps it under `<storagePrefix>.build`, space-separated in the guide's order, and nothing when there's none; another tab follows through the storage listener (`useThemeEffects.ts`). It reads only the ids the guide names, and writes back any saved id it doesn't name, so a tab on an older build keeps a leaning a newer build added. A leaning is retired by listing its id under `builds.retired`: Lordran's Humanity (`hum`) went with the Chaos weapons add-on on 21 Nov 2026, so "str dex hum" now reads as Quality and "pyro hum" as Pyromancer, and the next save drops `hum` instead of writing it back, so a tab still on the older build doesn't read a pick the reader has since cleared ("pyro hum" cleared to "hum") as a Humanity build. Until that save, the older tab keeps reading its Chaos add-on. A retired id is never a leaning again, since it would come back in every pick not yet saved again with a new meaning (`data.test.ts`; Lordran's `guide.test.ts` pins `hum`).
- **Its name** comes from the named builds (`buildOf` and `buildName` in `guide.ts`): a pick equal to a named build's leanings is that build ("pyro" is Pyromancer); otherwise the largest named build inside it whose remainder is exactly add-ons ("str dex pyro" is "Quality + Pyromancy"); anything else is a custom pick, called by its leanings' words. A custom pick gets steps, never picks or a weapon track: guides recommend for named builds. A pick reads notes once the guide has notes for every build in it (`readsNotes`); until then it reads as a custom pick does.
- **The dialog** (`BuildScreen.tsx`, `{ kind: "build" }` in the one DialogHost, Base UI Dialog): the named builds as cards (`CardRadioGroup` in `controls.tsx`, Base UI's radio group, each radio named by its title and described by its line, its note and its chips; the note, kept on a phone where the line goes, says how guides start the build: "Starts as a Pyromancer, with the Hand Axe"), the add-ons as switches in a fieldset below, each described by its line (they wait for a build to be chosen, since an add-on alone would pick one: Pyromancy alone is Pyromancer; one the build already holds shows on and locked), and Pick stats yourself, a Base UI collapsible holding the leanings' checkboxes for any custom set (open when the saved pick is one). Nothing is kept until Save build. Changing a build has no button that reads like a way out and loses the pick: Close and Escape leave it as it was, and Clear build, set apart from Save and shown only when a build is saved, says what it does. It's opened from the strip and the Progress page. Guide settings no longer holds the build.
- **The welcome** is the same screen with `welcome: true`, titled "How are you playing?": asked once, on the reader's first tick in a guide with builds (`changeChecks` in `actions.ts`, a tick a reader made: a sync or an import never goes through it), never on load, so a visitor from search, Lighthouse and the screenshots, which tick nothing, meet no dialog. Its way out is Just the checklist, which keeps no build. A first Check all asks too. It saves `<storagePrefix>.build-asked` once it shows (the screen's mount), so closing it any way answers it, and it never comes back; a welcome whose chunk can't be fetched (offline before the idle preload) never shows, isn't spent, and the next tick asks again (`loading.test.tsx`). The modal hides the tick's toast, so the toast, Undo and all, is shown again as the welcome closes. A reader whose `.build` holds a pick counts as asked. The asked key is apart from the pick's because a tab still on an older build removes `.build` whenever it saves settings with no pick, so an empty pick couldn't say "asked". Tests start asked (`test/setup.ts`); `builds.test.tsx` clears it.
- **The strip** (`BuildStrip.tsx`) sits under each chapter's banner, on every chapter at every size: the build's name and how many rows the chapter has a note on for it ("notes on 2 rows in this chapter": rows, since a build and its add-on can each have a note on one), or, for a pick that reads steps, how many steps ("3 steps in this chapter"), with Change build; with no build, an invitation (or, once skipped, "No build chosen") and Choose build. Not on a hidden chapter.
- **On a row** (`BuildMark.tsx`): the build's note under the row's words, on a rail of the guide's colour (`--build-line`, its primary softened toward the surface), in the row's type: one size down in prose, the row's own size and muted tint in a compact list or a checklist row. The build's name leads it in small capitals, read as "For your Paladin:". No tag beside the title, no step numbers, no chips: the note is the build's one line (the user's pick of four looks on 22 Nov 2026, the "rail"). A note with a pick under it ends with **Who says so**, a Base UI Popover naming each pick and the sites that recommend it for the reader's build (`whoSays`, names only: a source is never a link); a note with none states game facts, as the row does, and has no button. A step's deadline (`before`) follows in bold (no guide has one under a note yet: Lordran's one deadline, Logan's catalyst, serves Intelligence, whose builds read steps). A pick that reads steps gets its steps on the same rail, titled. `BuildLines` checks first, from the data alone, whether the row has anything (`hasBuildLines`), and only such a row reads the pick, as one string, so a new pick redraws those rows and leaves every other memoised `RouteRow` alone. Inside a prose row's `<p>` the words are spans shown as blocks, and the trigger, a `<button>`, is phrasing content; it sits above a checklist row's stretched label (`relative z-1`).
- **The popover** is one for the page, as the icon buttons' tooltip is: each Who says so is a detached `Popover.Trigger` on the handle in `who-says.ts` (`WhoSaysTrigger`), carrying its note's lines, and the popover itself (`WhoSays.tsx`, with floating-ui under it) is a chunk that `WhoSaysHost` warms once the page is idle and a build is picked, in a guide with builds only. A tap that comes first loads it and opens it on that trigger (`handle.open`; `loading.test.tsx`).
- **Your build** (`BuildPanel.tsx`), on the Progress page under Chapter progress, address `/dashboard/build`: first the build's Main weapon track (`weaponTrack`), a skeleton: the weapon its start names, with the class and what guides say it's for, then each stage its notes name ("Mace +5", "Divine Mace"; the named build's own, never an add-on's), with the role of the row's weapon or path pick as a word where there is one, in route order, revealed chapters only, each a dot filled once its row is ticked and a name that jumps to the row. Only the start has words: the plan under it holds them. Where a weapon's paths part (Normal or Divine, Divine or Occult) the stages run on in route order, one line, and their names say which path each is on ("Mace +10, on the Normal path", "Occult Mace, if you take it"): a tick says an ember was taken, not which way the reader went. A pick that reads steps has no track, and the panel says it holds the steps to the build. It says nothing of hidden chapters but that more shows as they're revealed: no count of hidden stages. Then the build's plan, chapter by chapter (`buildPlan`), revealed chapters only, each chapter a Base UI collapsible open while anything in it was unticked when the page drew it, each row that has something for the build with its box, ticked in place, its note on the same rail as the row's (named only beside an add-on, since the panel is the build's), and Jump to. A chapter doesn't close as its last row is ticked, so the list stays under the pointer. A line says how many chapters spoiler protection still hides. Drawn in every guide with builds, with or without a pick, so its address means the same either way; without a pick it says how to choose one.
- **Why the pick stays on the device.** It is a lens, not progress: losing it costs a tap, never a tick. A key of its own also survives a stale tab, which a field in `.v1` wouldn't: a tab on an older build writes its `validateState` copy back on its next tick, without fields it doesn't know. It isn't in backups either. Syncing it later wouldn't need the API first, since the ledger takes any `x:` leaf (`services/sync/src/ledger.ts`), but `flatten` and `viewFrom` give every `x:` leaf to the guide's `extra`, so it would need a reserved path of its own, one boolean per leaning so picks on two devices merge.
- **What it never does:** count, change a target, or reach a hidden chapter. A step is done when its row is ticked, so it has no progress of its own. Search and the checklist's filters don't read the lines.
- **Tests:** `data.test.ts` holds, in every guide, the leanings (each used by a build or a step), the named builds (known leanings, no two of a kind alike, each named by its own leanings, a start on a guide for it and two hosts, a weapon and a step for every one and a weapon on the track of one with notes), the picks (named builds, and for each a guide for that build and two independent hosts, a role, needs in the guide's leanings, no build given one item twice on a row, reader text), the notes (one per row for each build with notes wherever it has a pick or an unquiet step, none without one under it, each pick named, no five-word run of the row, a stage for one build on every weapon's row, no scaling letter), the quiet steps (only builds they serve, never a deadline, never where the build has a pick), no "best" in any string a build shows, no build id shown as text, the retired ids (never leanings again), the steps (real rows, a deadline only on two hosts and off a missable row), the plan (no hidden chapter; notes for a pick that reads them, steps for one that doesn't, deadlines either way; a build with an add-on reads notes only when both have them) and the weapon track (its start first, its notes' stages, route order, revealed chapters only, nothing for a pick that reads steps, nothing changed by an add-on). `builds.test.tsx` holds the pick and the asked key (a save keeps a leaning a newer build added and drops a retired one), the names, the welcome on the first tick and never again, the dialog's cards (and how each build starts) and add-ons, the row's note and its lead, Who says so (names, never links), the steps for a pick that reads them, a build with notes beside an add-on without (steps, led by the whole pick's name), the track, the plan, and nothing at all in a guide without builds. Each guide's `guide.test.ts` pins `BUILD_KEY` and `BUILD_ASKED_KEY`, and Lordran's its leaning ids, the retired `hum`, every starter against its build's starting classes, and that a later pick's note says when. The `BuildNote` story draws the rail in prose, a list, a checklist row and the plan, a pick's steps, a deadline, and Who says so with its popover open, under axe in every look (the stories' guide has no builds, so its words are made up); `CardRadioGroup`, `CheckboxGroup`, `Switch` and `Tag` (AllTones draws every tone) cover the rest, and the track's ink, muted and primary on its soft card are pairs `theme.test.ts` holds to contrast.

## Overall completion

One figure says how far through the guide a reader is (`overall` in `guide.ts`, drawn by `Overall.tsx`): over the chapters in the rail and the chapters drawer, as the Progress page's hero, and in the guide page's line under Next up. Decided 18 Nov 2026, when Echoes and Lordran had no overall figure and Koholint's counted rows.

- **What 100% is: every target on the guide's board, each item once.** Every board target counts, counted as the board counts it (an entry by one, the `quantity` category by amount) and only up to its `goal` (`listedPercent`). What's left counts the same targets the same way, so the figure is 100 exactly when What's left is empty (`overall.test.tsx` holds that in every guide). A row counts once per target it carries, so a row that is two kinds of item keeps only the target of its real kind: a quest step that is also a charm counts as the charm (Hallownest), a Snuggly trade that is a spell or a slab counts as that (Lordran), a chest that awards an accessory counts as the accessory (Echoes). Where one idea would count twice, a second tag names the rows that count (Echoes' dungeon chests are also chests, so the overworld ones carry `overworld-chest`). A game's own lists stand as the game counts them: Echoes' side quests that award an item the board counts (a bottle, a heart, an accessory, crystals, an automaton, an outfit, an echo or a stamp) are each two items on two game lists ([the rules](#the-completion-rules), rule 4). Echoes' dungeon chests are not a game's list: no page read totals them, so their goal (57) is the guide's own sum, and the two that award accessories count as those accessories, once. Each category weighs by its size, not equally: four Fairy Bottles weighing what 127 Echoes do would move the bar two points a bottle. **Only what lies outside the game stays out, such as amiibo, which need physical figures** (`completion.outside`: a row with one of its tags never counts, and a board target with one is shown and left out of the bar and What's left): everything else a guide tracks that a reader gets or finishes is a target, whether the game totals it (`list: "game"`) or it is the guide's own list (`list: "guide"`; its goal is its rows, and `facts-to-verify.md` says it is no game total). Steps the game doesn't credit are directions and carry no target (rule 2). The rows of a one-way choice (Frampt or Kaathe, the Nailsmith) are ordinary counted rows: the recommended way in the choice's chapter, each other way in a later playthrough's ([One-way choices](#one-way-choices), rule 6). A game that keeps a percentage of its own has that figure in its panel, not in the bar: Red Dead's estimate of Stats → General, and Hallownest's points over 112, are each in a "Check against the game" panel, worded as the save's or the game's figure and never a bare percentage beside the bar's. Decided 19 Nov 2026: the bar had read the game's points in Hallownest (#74) and Red Dead's weighted estimate, Hallownest's extras and Lordran's NPC quests were `optional` targets, and Red Dead's scraps and optional tasks sat outside its estimate; now every guide reads this rule, so a reader's bar reads differently from before for the same ticks (lower or higher, by what they have ticked: with chapter 1 ticked, Red Dead's reads 43 where its estimate read 40.7), and no saved data changes. Figures when the list first came in, after chapter 1 ticked whole: Koholint 12% (10% when it counted its 400 non-amiibo rows), Echoes 7%, Lordran 4%. The weighted-model options (`completion.overall.percent` and its label, `isCore`, `left` and `unit`) were taken out of core the same day: no guide used them, and a game's own percentage belongs in a panel, so the figure and What's left read the board alone.
- **Achievements count only as the game's own.** A target, category or row named after achievements needs the game to keep a list of its own (`GuideConfig.achievements`, sourced; [chapter-data.md](chapter-data.md#achievements)); `data.test.ts` walks the config with `readerText` (its own export, `reader-text.ts`, so no page loads it) and fails on the word anywhere a reader sees it otherwise. Panels give only their titles to the walk, so a panel's body is the one place it can't check. Lordran's 41-achievement target went on 19 Nov 2026: its rows count as their real kinds, once each.
- **Rounded down, the percentage alone.** `pct` rounds down, so 100% never shows while anything on the list is left. There's no "n of m" beside a list's figure: its total adds crystals by amount and counts a row once per target, so it isn't a count of anything a reader could find.
- **Spoilers.** The board's totals already count hidden chapters, so the figure tells nothing new as long as it stays one fill: no chapter's share, no mark for what's revealed (either would tell how big a hidden chapter is), and nothing that names what's left. Revealing a chapter changes no tick, so the figure stays put. It carries `data-nosnippet`, so a search result doesn't quote a first visit's 0%. Echoes' chapter 9 holds 51% of its list and Lordran's chapter 11 43% (the sweeps before the first ending): a reader who has finished every revealed chapter can see a lot is left, which What's left already says.
- **The bar.** Base UI's Progress, `role="progressbar"`, named "Overall completion" by its visible label (`Progress.Label`), its value text ours (`overallText`: Base UI's own goes through `Intl` and reads 99.9 as "100%"). The guide page's line under Next up carries `data-nosnippet` as well. Not a meter: ARIA keeps that for measurements, not progress. Not a link, since a progressbar inside one muddles the link's name; the Progress page is a tab away. In the rail it sits under the heading and outside the chapters' `nav`, and takes no focus, so the drawer's first focus is unchanged. The fill eases over 200ms, and not at all under reduced motion (`app.css`). It is `--primary` on `--bar-track`, 5.1:1 (Lordran, light) to 8.0:1 (Red Dead, dark) when it came in.

## The completion rules

What 100% means in every guide, as settled on 18 and 19 Nov 2026 (the drift check of 19 Nov held all six guides to it; its four decisions are at the end). Under each rule, *Held* names the test that holds it, and *Not held* names what no test can check, which review reads instead (the `reviewer` and `source-checker` helpers). Since 20 Nov 2026 the rules are held in core, by `data.test.ts`'s "the completion rules", which runs in every guide, and the guides' hand-written copies of those tests are gone. The guards read what each guide declares in its config: the tags that label its route steps (`completion.directions`), what lies outside the game (`completion.outside`), and whose list each target is (`list`). Those declarations are the guide's own, so review reads them too.

1. **Everything the guide tracks counts.** Every row a reader gets, finishes or collects carries a board target, and 100% is every target to its goal (`listedPercent`, [Overall completion](#overall-completion)). Fast-travel points count with the rest: Koholint's warp points, Hallownest's Stag Stations, Pharloom's Bellways and Ventrica stations, Echoes' Waypoints. *Held:* `overall.test.tsx`, in every guide: 100 with every row ticked, under 100 with any one target's row left, and a row on no target adds nothing. `data.test.ts`, in every guide ("counts every row but its directions and what lies outside the game"): a row whose first tag is no direction, and that carries no tag outside the game, must carry a counted target, so a category added to the data and left off the board fails. Echoes' `guide.test.ts` pins its 43 Waypoints (17 overworld, 26 inside dungeons), and Red Dead's that its board is every category but its Stranger steps. *Not held:* what a guide names as a direction. A new kind of row whose tag is added to `completion.directions` counts nothing and passes.
2. **Steps the game doesn't credit never count.** A row's kind is its first tag. A row that only moves the reader on (go, talk, ride, open) is a route step: its first tag is one of the guide's `completion.directions` (`route`; `story` in Koholint, and in Echoes beside `route`), and it carries no target. So is a Stranger task's step before its last, tagged `stranger-step`, which Red Dead counts once, by the last. A direction tag after another kind is a filter: Koholint's instruments (`["instrument", "story"]`) and Red Dead's Stranger finals (`["stranger", "stranger-step"]`) count as their kind. Something the game itself lists and credits counts even on the critical path: a boss, an instrument, one of Red Dead's 57 story missions (credited in Stats → General, two hosts say 57). Red Dead's optional tasks (I Know You's three parts and Solomon's Folly, which its 100% leaves out) are things a reader finishes, not directions, so each counts: the rule is about steps, and they are the guide's own list. *Held:* `data.test.ts`, in every guide (the same test): a row whose first tag is a direction carries no board target. Koholint's `guide.test.ts` goes further (no row led by `story` carries a second tag), and Red Dead's pins its Stranger steps at nothing and its 57 story missions as counted. *Not held:* that a row's first tag is its real kind. A step tagged `["boss", "route"]` counts as a boss.
3. **Nothing stays out but what lies outside the game.** Amiibo, which need physical figures, are the only tag in `completion.outside` (Koholint and Echoes). A row carrying one never counts, and a board target with one (Koholint's amiibo tile) is shown and left out of the bar and What's left. *Held:* by construction, since core counts every board target but those (`guide.ts`), and `data.test.ts`, in every guide: a row outside the game that carries a counted target fails (the same test), and a direction is never on the board ("names its direction tags…"). *Not held:* what a guide puts in `completion.outside`.
4. **One each: an item counts once, per item.** A row counts once per item it gives, and an item counts once however many rows mention it: a row that only yields an item another row counts is a route step. A guide's own list never recounts a row another target already counts, and a second tag names the rows that count (Echoes' `overworld-chest` and `minigame-extra`). A game's own lists stand as the game counts them: an Echoes side quest and the accessory it awards are two items the game lists, so they stay two, as a Koholint Dampé challenge and the Heart Piece it awards do. *Held:* `data.test.ts`, in every guide ("never counts a row of the guide's own lists under another target"): every target says whose list it is (`list: "game"` or `"guide"`, which the type requires), and a row on a guide's list carries no other board target. Hallownest's and Lordran's `guide.test.ts` go further: no row under two targets at all, game lists included. Echoes' pins which chests and minigame entries carry `overworld-chest` and `minigame-extra`, and Lordran's that each item a later cycle gives sits in chapter 13, that the steps that only yield one or repeat something are route steps, and that its later-cycle list is the other ways at its one-way choices. *Not held:* that an item is counted by one row only (two rows that give the same item, which only the sources tell), and which of its targets a guide calls its own list.
5. **Every target has a goal, and every goal has a source.** For a game's total, the guide's `facts-to-verify.md` names two hosts. For a guide's own list, the goal is its rows, and the file says it is no game total. *Held:* `BoardItem.goal` is required by the type, and `data.test.ts`, in every guide ("gives every target a goal, exactly its rows as the board counts them"), so a goal above or below its rows fails. Koholint's and Red Dead's `guide.test.ts` pin every goal's value too, and Pharloom's its game's eleven and its own four. *Not held:* that `facts-to-verify.md` records the hosts. Red Dead's (Counts) names two hosts for each of its counts, the 30 scraps as five outfits' six each, except the optional tasks, the guide's own list.
6. **One-way choices.** The recommended way is a counted row in the choice's chapter. Each other way is a counted row in a later playthrough's chapter: NG+ and NG++ in Lordran's chapter 13, "A Second Save" at the end of Hallownest and Pharloom. An ending that needs another save goes there too; endings one save can reach in order are missables. *Held:* `data.test.ts`, in every guide: real rows, a later chapter for each later way, a row in one choice at most, the recommended row never a missable, two independent hosts, and every way, recommended and later, carries a counted target ("counts every way of a one-way choice"). Lordran, Hallownest and Pharloom pin where the later way sits. *Not held in core:* that the later chapter belongs to a later playthrough, since no config marks a playthrough's chapters. The three guides' pins hold it for theirs.
7. **Achievements only where the game keeps its own list.** That needs `config.achievements`, with two hosts. Otherwise no string a reader sees says achievement or trophy. *Held:* `data.test.ts`, through `readerText`, which is blind to a panel's body ([Overall completion](#overall-completion), Achievements).
8. **A missable needs two independent hosts that state its condition.** Anything weaker, and every unconfirmed count, weight or claim, goes in the app's `facts-to-verify.md`, in the same commit as the data. *Held:* `data.test.ts` checks a real row, https, a why, and two different hosts. *Not held:* that the hosts are independent beyond their address (a wiki and its fork are two hosts and one source), that they state the condition, and that `facts-to-verify.md` records what is weaker.

Decided 19 Nov 2026, after the drift check: "one each" is per item (rule 4), Echoes' 43 Waypoints become a target, the guide's own list with a goal of 43 (rule 1), Red Dead's 57 story missions stay counted and the rule reads "steps the game doesn't credit never count" (rule 2), and a Lordran NG+ item counts once: its game-list row moves to chapter 13 with its id unchanged, the cycle row that only yields it becomes a route step, and a source check settles whether the Speckled ring becomes the Siegmeyer choice's later way (rule 4). Where a choice's way only yields items, one row counts them: a later way is the item's own row (Lordran's Speckled ring and Abyss Greatsword), and a recommended way, which must be the choice's own row, counts what it gives, and the items' rows are route steps (Lordran's Ciaran trade and its two Tracers; the user's decision, 19 Nov 2026). A guide that doesn't match yet is brought in line by a card of its own, and a row's id never changes in the move.

## The page shell

- `index.html` is core's, filled in per guide by `vite.ts` from the brand: title, description, theme colour, corners, storage prefix and the `@font-face` rules. In dev, core's plugin serves it for any HTML navigation, so deep links like `/guide/3` work under `pnpm dev`.
- **`theme-init.js` stays an external file.** It sets `data-theme` before the first paint, so the page never flashes the wrong theme. The CSP every guide sends has `script-src 'self'`, which blocks inline scripts. `vite.ts` serves the file in dev and emits it in the build, and the service worker precaches it. `deploy.test.ts` fails if core's `index.html` template gains an inline script, or the CSP allows one. It doesn't see the built page, so after a change to the Vite plugins, check `dist/index.html` for injected scripts too.
- **One frame on a wide screen.** The rail and the page are one block, at most `--frame-max` wide (80rem, 1280px at the default 16px, `tokens.css`), centred: `Layout`'s grid is a band, the rail's column, the page's column (`--page-max`, what's left of the frame beside the rail) and a band, and the two bands share whatever the screen has past the frame. The left band is drawn in the rail's tint (the grid's `::before`), so the rail runs to the screen's edge; `<main>` spans the page's column and the right band, so it reaches the window's edge too, and the page inside it (the `/page` container, with the gutter) is at most `--page-max`. The top bar's contents sit on the same frame: an inner grid, `mx-auto` and at most `--frame-max`, so the brand stays over the rail, the buttons end over the page's edge and, with room, the pages are centred over the page's column ([the top bar](#the-installed-app)). Below 1280px nothing is spare and the frame is the screen. It is the same in a browser tab and in the installed app; in the app the band left of the rail takes no wheel (it is neither the rail nor `<main>`), a choice. Layout's `WideFrame` story and TopBar's `OnTheFrame` hold the columns at a 2000px screen (a story draws the whole frame with a stand-in for the service worker's hook, `.storybook/pwa-register.ts`). **The number bounds the article's lines.** The article's card and text fill their column with no measure of their own, so on a wide screen the frame is what keeps a line of prose readable: at 1280 the first chapter's paragraphs run 79 (Koholint, DM Sans), 83 (Echoes, Nunito) and 89 (Lordran, Source Sans 3) characters a line at the median, measured on 18 Nov 2026 at 2560px. The frame before it (the rail plus a 1460px page, 1709px) ran 135, 138 and 152. Until 18 Nov 2026 the 1460px limit was the page's alone, so on a wide screen the page floated away from a rail pinned to the left edge (106px apart at 1920, 426 at 2560) and the top bar's buttons sat at the window's edge.
- **The page fills the screen's height.** The frame's one row is the room under the top bar: at least the screen less the bars in a browser tab (`min-h` on `Layout`'s grid), exactly the room the fixed frame leaves in the installed app (`minmax(0,1fr)`), and the grid is one column from 800px down in both. `<main>`, the page (`/page`) and each kept page's element (`Pages`) are flex columns that grow into what is left of it. So a page can sit something in the middle of that room with auto margins and no height worked out for it (the hidden chapter, below): the middle of `<main>`'s content box, a few pixels above the screen's middle (6 on a phone, 12 on a desktop), since `<main>` keeps more room under a page than above it. A page taller than the room is as tall as it needs, as before: a growing flex item never shrinks under its content. Every other page's root is the one item of those columns and grows nothing, so it lands where it did as a block. Seen on 19 Nov 2026 in Chrome and Playwright's WebKit, in a tab and with the app's frame faked, at 375, 768 and 1280px: a long chapter's and the Progress page's scroll height and the room under them are what they were, and the guide, checklist, Questlines and Progress pages draw as they did; not seen on a phone. Layout's `HiddenChapterInTheMiddle` stories hold the centre through the real frame.
- **A hidden chapter** (`/guide/N` past the reader's ceiling, `SealedChapter.tsx`) is centred in that room, over a veil: a crossed hatch in the guide's primary that fades out to its edges, where a revealed chapter has its banner. It shows the chapter's number (`ChapterNumber`, the hero's tag) and the rail's teaser for it, never its title, art or region, then "Not revealed yet" ("Chapter N: Not revealed yet" to a screen reader), why it's hidden and which chapters revealing it also reveals, and two ways out: Reveal chapter N, the hero's accent look, which asks first (`useReveal`), and Back to chapter <ceiling>. The page's title stays "Chapter N is hidden" ([search engines](#search-engines-and-link-previews)).

## Search engines and link previews

A crawler keeps no storage between pages, so it always sees a guide as a first visit does: chapter 1 open, every later chapter hidden. That decides the policy (decided 17 Nov 2026): nothing past chapter 1 is ever shown to a crawler, so nothing past chapter 1 can reach a result's title or snippet. One exception, by design: a one-way choice's block names its later ways, rows of a later playthrough's chapter, by title and chapter number, and those titles say only what the choice's chapter says ([One-way choices](#one-way-choices)); the list carries `data-nosnippet`, so a result doesn't quote it. Serving crawlers the later chapters would put spoilers in results and show them a page readers don't get. The price is that a search for a later chapter's item doesn't find the guide.

- **Indexed: `/guide/1`, `/checklist` and `/dashboard`** (`INDEXED_PATHS` in `src/search.ts`). `headFor` gives every address its title, description, canonical and robots rule. Each of the three is its own canonical on `brand.home`, which is why `home` is required. Every other address names one of them: `/guide/1/<entry>` and `/guide/99` name `/guide/1`, `/checklist/<category>/<chapter>` names `/checklist`, and `/` and unknown addresses become the chapter they open at. `/sources`, the Sources page that sources leaving the guides removed (17 Nov 2026), is one of those: the router's catch-all opens the reader's chapter (`Navigate replace`), with no server redirect, since an installed guide's service worker answers its navigations anyway and every `vercel.json` stays the one file `deploy.test.ts` holds. A hidden chapter says `noindex` and its title is only "Chapter N is hidden". A revealed chapter is titled by its name, which only a reader who revealed it sees. The descriptions are templates filled from `brand.game`, `brand.name` and the checklist's chip labels, so a guide writes none: they quote no counts and claim only what the app does. `search.test.tsx` holds them under 160 characters, with the game named, and checks that no address a first visit can reach names a later chapter.
- **Not indexed: `/questlines`.** A crawler sees chapter 1 alone, so the page would hold what `/guide/1` does. `headFor` gives it its own title, its own canonical and `noindex`, and `/questlines/<line>` names it as canonical.
- **`Head` (`components/Head.tsx`)** applies `headFor` for the address shown and what is revealed, so a reveal at the same address drops the `noindex`. It sits in `App` once, not in each page, because a page stays drawn while hidden (`Pages`). It edits the shell's own `<title>` and description, so there is only ever one of each. The canonical and the robots rule exist only there: Google advises against a canonical in the raw HTML that the page's script then changes. Lighthouse's canonical audit doesn't compare hosts, so a canonical on production passes on a local build.
- **The shell's link preview** (`index.html`) is the same on every address, because Slack, Discord, iMessage and X never run the page's script: `og:` tags with the guide's title and description, a `summary_large_image` card, and a WebSite JSON-LD block (`seo.ts`'s `websiteJsonLd`, with `<` escaped) for the site name Google shows above a result. The JSON-LD block is the template's one inline `<script>`. A data block never runs, so the CSP doesn't cover it, and `deploy.test.ts` allows exactly that one. The `%GUIDE_*%` values are escaped as they're filled in. The picture is a 1200×630 JPEG cut at build from chapter 1's banner, which every first visit already sees, leaning right of centre where the banners keep their detail (`seo.ts`'s `ogImage`). It's named by its content (`assets/og-<hash>.jpg`), since previews are cached by address, and it's left out of the precache.
- **robots.txt and sitemap.xml** are emitted by the build (`seo.ts`'s `searchFiles`): every crawler let in, AI ones included (the user's choice), `/api/` kept out, and the sitemap listing the three pages on `brand.home`. Vercel's filesystem step serves them ahead of the catch-all. The service worker's navigation fallback skips `.txt`, `.xml` and `.jpg`, so a reader who opens one in a tab gets the file, not the guide. Hidden chapters are left out of the sitemap but not blocked, because a blocked page's `noindex` is never read.
- **A hidden chapter's place name in the rail** (`teaser`) is shown to everyone, crawlers included, and carries `data-nosnippet`, so Google doesn't quote it as a result's snippet. Google reads that attribute on a span, which is why it sits on the teaser and not on the row's button. Whether Bing honours it isn't verified. A teaser is public either way, so it must never be story.
- **No prerendering.** Google and Bing run the page's script, and DuckDuckGo, Yahoo and Ecosia use Bing's index. A crawler that doesn't run it sees the shell: the guide's title, description, picture and a `<noscript>` with its name and description.

## The installed app

A guide added to the home screen (or installed from a browser) is meant to behave like an app, not a page in a window. A guide in a browser tab stays an ordinary website. Everything here is core's; a guide sets nothing for it, and none of it is hand-written CSS: it's Tailwind classes in the components, and the few global rules are in `app.css`'s `base` and `components` layers.

- **How the page knows.** `theme-init.js` sets `data-standalone` on the root element before the first paint when the guide was opened as an app: `navigator.standalone` (iOS Safari's own flag) or `(display-mode: standalone)`. `app.css` turns the mark into a Tailwind variant, `standalone:`, that matches the root element and everything in it, so `standalone:overflow-hidden` is a class that applies in the app and nowhere else. `shell.test.ts` runs `theme-init.js` against stand-in pages and fails on a rule in `app.css`'s `base` layer that isn't keyed on the mark (the one exception is the scroll padding under the top bar, and over a phone's tab bar, which every page has).
- **The frame's widths are variants too.** They are the screen's decisions, and only those: `mid:` (under 1041px: the rail narrows, and the brand's padding with it), `drawer:` (800px and under: the rail is a drawer, the top bar is shorter), `phone:` (550px and under: the pages move to a tab bar at the bottom and the top bar becomes a title bar), `slim:` (405) and `tiny:` (360), all in `app.css`, in em (the px at the default 16px; [sizes in rem](#styles)). They are inclusive, as the media queries they replaced were: Tailwind's own `max-[800px]:` is `width < 800px`, which would have missed an 800px screen. They're declared widest first, so the narrower wins. `--bar-h`, `--rail-w` and `--tabs` change at the same widths, in `tokens.css`. Where the layout differs in what it renders, not only in how it looks (the rail or the drawer, the top nav or the tab bar, the checklist's filters on the page or in a sheet), JavaScript reads the same widths (`useNarrow` and `usePhone` in `useNarrow.ts`) and renders one, so a landmark or a field's id is never in the page twice.
- **A part lays itself out by its own width, with a container query.** The chapter's hero (`ChapterHero`, container `hero`) puts its banner above its words under 40rem, picked from the art and the words: under it the words column, 59% of the hero, leaves a two-line title and two buttons little room beside the art. Side by side the hero is a short card at any width over that, about 265 to 330px tall for a one-line title (more for Lordran's three lines), where stacked it is 440 to 540px. Its title is a `cqi` clamp, so it scales with the hero. The chapter's article, the Progress page and the Questlines page list their parts with one part, `Contents` (container `contents`), which folds the list above them under 52rem, so it stands beside the prose only where the prose keeps about 570px; `<article>` is a container too (`article`), so a section's padding and title follow the column it has. What's left (`WhatsLeft`, container `left`) puts a category's bar under its name under 28rem. The page inside `<main>` (`Layout`'s inner `div`, at most `--page-max`) is the page's container (`page`), so a page's title (`PageHeading`, the route's "Chapter route") is a `cqi` clamp of the page column. The Progress page's board is `auto-fill` columns of at least 14rem, three at most, with no query. The wrapper is the container wherever the part's own classes change (a container can't query itself), and every query names its container; `cqi` can't be named and reads the nearest one, which is why nothing sits between a section and its article. So a story draws a part at any width in a plain `div` and gets the layout that width gets in the app. `sizes` can't read a container, so the banner's `BANNER_SIZES` names the screen widths where the hero is surely stacked and asks 1,320px everywhere else, about the most a side-by-side banner is drawn (the comment there has the one exception, and why it isn't asked for). Container queries resolve in the same style and layout pass as media queries: no shift after the first paint. A phone's tighter spacing (a part's padding, the hero's intro going, its smaller corners) stays `phone:`: that follows the screen, as the gutter does. Until 18 Nov 2026 the hero stacked under a 1050px screen and the article folded under 1000px (`stack:` and `fold:`), so a 734px hero at 1050px stacked and the same hero at 1051px didn't, and at 1024px the prose was 475px beside its contents (fluid-layout audit, batch C).
- **The Questlines page is one column, with "On this page" beside it**, as the Progress page is (below). From 18 Nov 2026 (#70) its cards went down two stacks of their own where two 22rem columns fit, the odd lines down the left and the even down the right, so a card that opened pushed down only its own column; since the same day (after #71) they are one list in route order at every width, each card under the one before, so a card that opens pushes down only the cards under it and none leaves a hole beside a shorter one. `Contents` lists the cards the chips show, one link per line to its address (`/questlines/<line>`), in their order, beside them from a page column of 52rem (a 1280px window) and folded above them under that; the chips stay above both. The list follows the chips so that a link always lands on a card: one to a card the chips hide would land on nothing, or change the reader's filter under them. It is drawn from the same lines as the cards, so it names no line the page doesn't show (spoiler protection, [Questlines](#questlines)) and carries no count. There is no list with one line met (Koholint has one at all), where it would only name the card beside it; that follows the lines met, not the chips, so a chip that leaves one card keeps the list. Nor is there one when the chips leave no card, only "No questline here yet." - **A fixed frame, installed only.** `#root` is `fixed` and fills the screen, the top bar, the rail and a phone's tab bar (the frame's last row) stay put, and `<main>` is the one thing that scrolls (`standalone:overflow-y-auto standalone:overscroll-contain`); the root and body have `overflow: hidden` and `overscroll-behavior: none`, and the body is `fixed` as well, so the page itself has nothing to scroll and the top bar and the rail never bounce. The main area keeps its own scroll, and with it whatever bounce the platform gives a scrolling area: `overscroll-behavior` stops it chaining to the page, not the bounce (and on iOS it is only partly supported: [caniuse](https://caniuse.com/css-overscroll-behavior) lists 16.0 and later as partial, and [WebKit bug 275947](https://bugs.webkit.org/show_bug.cgi?id=275947) reports that `none` and `contain` don't stop pull-to-refresh in Safari). - **Where the reader was, in every mode** (`store/place.ts`, `Layout`). Each page keeps its scroll offset (the window's in a tab, `<main>`'s in the app) and its filters (`useKept`: the checklist's category, chapter, status and search, a chapter route's category and status) while the guide is open. A reader *coming back* finds them as they were: a tab of the bar (`MainNav`'s links carry `state: { restore: true }`, and the Checklist tab goes to the last checklist address), or Back and Forward (the router's POP, read per history entry, so the same chapter twice in the history comes back at each offset). Any other link is a new visit: the top of the page and the filters the address gives. A "place" is the page without what an address points at (`placeOf`: a guide entry or section, a progress panel), so an entry link and its chapter share one. When the guide goes into the background (`visibilitychange` to hidden, `pagehide`) the current place, its offset and its filters are saved under `<storagePrefix>.place`; `restoreLaunch()` in `main.tsx` reopens it, before the router reads the address, only when the guide opens at exactly `/` (the manifest's `start_url`; a deep link always wins), and only if `safePlace` still accepts it: a page the guide has, a category it has, and no chapter the reader's settings now hide (otherwise Home's chapter, as before). The scroll is restored in a layout effect, which runs after the page's own (the guide's entry and the progress panel scroll in layout effects too), so the page is in place before it is shown.
- **Pages kept between tabs, in every mode** (`Pages.tsx`, in `App` where `<Routes>` was). Each of the four pages (Guide, Checklist, Questlines, Progress) stays drawn once seen, under React's `<Activity>`: hidden (`display: none`, its effects stopped) while another is on screen, shown again as it was when the reader comes back to it (a tab, Back or Forward), so a tab switch reveals a page instead of building it, like a phone's tab bar. A new visit (a link from another page) builds it afresh from the address, by keying its routes on the history entry it began at; a move within the page on screen is left to the page's own keys (GuideView's chapter, ChecklistView's address). Each kept page draws its own last address (`<Routes location>`), which React Router reports as a POP, so `useReturning` reads the real answer from `Arrival` (`store/place.ts`), set per page at its arrival. A hidden page's store subscriptions are effects, so it catches up with the progress as it comes back. `useShowing()` (`store/place.ts`) numbers each showing of a page (null while it's out of sight): the checklist's filter sheet is open only in the showing it was opened in, so the page comes back without it. Closing it in a render of the hidden page wouldn't do: React runs that render at its lowest priority, maybe not before the page is back (an open select closes by itself: the focus leaving it is a state change of its own, which React applies as the page comes back). And a sheet must be gone before its page hides, not only closed, or it slides away over the page when it comes back (a hidden page runs no transition and no effect, Base UI's included): on Back or Forward the sheet closes and unmounts at once (`Sheet`, through `useBeforeBack` in `beforeBack.ts`, a popstate listener that `main.tsx` adds before the app, so ahead of the router's, inside which React draws the next page; browsers call a window's listeners in the order they were added). `sheet-probe.mjs` in the `guide-check` skill checks it frame by frame. The tab bar marks a pressed tab at once (`MainNav`), since the router's move is a transition that keeps the old page and address until the new page is drawn. No id may be in two pages (a row on the checklist has no `entry-` id: its chapter's page, which may be kept beside it, has it; `Layout.test.tsx` checks). There is no page transition: the fade #33 added took a picture of the whole page, tens of thousands of pixels tall on the checklist, and in iOS Safari (the iOS 18.7 simulator, WebKit 27.2) and Playwright's WebKit every move away from Red Dead's checklist then froze the screen for 15 seconds, blank for part of it. `tab-switch.mjs`, `sim-tabs.mjs`, `tab-trace.mjs` and `reveal-probe.mjs` in the `guide-check` skill measure it. Seen in Chrome and Playwright's WebKit at phone size, all three guides, and in the iOS simulator's Safari (Red Dead); not on a device.

The rule is therefore for the installed app only (`standalone:`), where `body` is fixed and is the containing block (the Simulator showed that case right with the earlier, unscoped rule; the scoped one resolves the same way there by reasoning), and a tab keeps the fixed backdrop. A tab with the fixed backdrop was looked at in the iOS 27.2 Simulator, scrolled well down (the dimming covers the page, and the band under the toolbar is as dark as the rest, where Base UI's own note says a fixed backdrop can leave it bright on iOS 26 and later) and in a desktop browser; on a real iPhone (iOS 18.7) it wasn't looked at after the change. (2) A touch that opens a dialog used to leave the keyboard-style focus ring round the first button or radio it focused, round something nobody pressed. After a touch the dialog itself takes the focus, except when the first thing is a field you type in, which keeps it because that is what brings the keyboard up; after a key press, as before, the first field. (3) The dialog body scrolls, and a scrolling box clips what sticks out of it, the focus ring included (it was cut off at the left and bottom edges): the body now takes in 8px of the dialog's padding on the left, right and bottom and gives it back as its own (the top isn't taken in: a ring on something at the very top of a body could still be clipped; nothing there does today). In the iOS 27.2 Simulator, (1) and the focus part of (2) were seen right, and (3) in part (the ring of the code field whole); on a real iPhone (iOS 18.7) none was tried after the change (the walk covers them). ## Styles

- Core ships one stylesheet, `app.css`, which `main.tsx` imports. It orders the cascade layers `theme, base, components, utilities`, loads Tailwind's theme, preflight (into `base`) and utilities, and pulls in `tokens.css`. It also holds the variants (`standalone:` and the layout's widths) and, in its own `@layer base` block, the few global rules: the installed app's frame ([the installed app](#the-installed-app)), the body's type and colours, the scrollbar and native controls in the palette, the focus ring every part relies on, a button's pointer, and reduced motion. Preflight brings the until-found exception for `[hidden]` (so find-in-page opens a closed collapsible) and the transparent tap highlight. There is no other stylesheet: `shell.test.ts` fails if a `.css` file other than `app.css` and `tokens.css` appears in `packages/core/src`, and on any rule in that base block that would make a browser tab a frame. A guide only sets the eleven palette colours in its `theme.css`, which loads after it.
- `tokens.css` holds core's design tokens: the colours derived from the palette, the status and category colours, the corner presets, the type scale and the layout sizes, in the `theme` layer. Its `@theme` blocks hand them to Tailwind as variables (`bg-paper`, `rounded-card`, `font-display`), never as copied values, so a guide's palette and corners reach every utility. Tailwind's own colours, radii, shadows, fonts and type scale are cleared: `bg-red-500` and `text-sm` don't exist.
- **Sizes in rem, widths in em.** Type, spacing and the layout tokens (`--bar-h`, `--tabs`, `--rail-w`, `--frame-max`, `--sticky-gap`) are rem, and the frame's widths (the variants in `app.css`, the matching media queries in `tokens.css`, `useNarrow.ts`) are em, each the old px ÷ 16, so at the browser's default 16px nothing differs from px. A reader who sets a larger default size (Chrome's and Brave's "Large" is 20px) then gets bigger text with everything around it, and the narrower layout sooner: at 20px a screen W wide gets the layout a 16px reader gets at 0.8 W, drawn 1.25 times larger, like zoom. Before 18 Nov 2026 the text was px and the controls rem, so that setting fattened the controls around text that stayed the same size. Px stays only where it isn't type or layout: borders and hairlines, the focus ring and its offset, underline offsets, radii, shadows, the safe-area insets, `--vv-top` (measured in JavaScript), and `BANNER_SIZES`, the banner's `sizes` hint. iOS Safari doesn't apply a default font size to a page, so on an iPhone none of this changes anything.
  - **The type scale** (`tokens.css`) is named after each step's size in px at 16px, like Tailwind's spacing: `text-14` is 0.875rem. A step sets the size only; the line height is inherited or set with `leading-*` or a slash (`text-16/[1.58]`). `leading-sm` and `leading-lg` are the line heights Tailwind's `text-sm` and `text-lg` carried, kept on the controls that had them. A value inside a `calc()`, `min()` or `minmax()` is written in rem.
  - **One spacing scale.** A margin, padding, gap or inset is one of Tailwind's whole steps (4px apart at 16px), one of the half steps 0.5 to 3.5 (2, 6, 10 and 14px), or `px` for a hairline (the tick box's own tokens aside, `ps-check-indent`): no quarter steps, no half steps above 4, no length of its own. A step inside a `calc()`, a `clamp()` or a variable's fallback is written in rem and is one of those too (`px-[clamp(1.5rem,5cqi,3rem)]`). `spacing.test.ts` reads core's source and stylesheets as text and fails on a class, a length inside one, or a spacing variable (`--pad-end`, `--button-px`, `--sticky-gap`) off the scale; lint doesn't check the scale. The same few rooms recur: a title and the line under it 1.5, an icon and its words 2, a row of buttons 2, cards in a list 3, a page's parts 3 and 5 under its heading (3.5 on a phone). The safe-area insets, `--vv-top` and the frame's gutter (a `vw` clamp) are the frame's, not steps. Until 18 Nov 2026 core carried about 70 one-offs from the screenshots it was first built from (13px beside 12, 7 beside 8), exact in rem but on no scale.
  - **What holds the parts keeps the room between them.** A stack is `flex flex-col gap-N` and its parts carry no outer margin: a page under its heading (`HeadedPage`), the chapter's page (its top, then the route), a route and its groups, an article, its sections and each section's steps, a `Panel` and its parts (`PanelHead` keeps a title and its opening words closer than the rest; `pad` sets the room inside and between, so the two can't be mixed). So a part that renders nothing leaves no gap, and nothing collapses. A stack is a flex column rather than a grid, because a grid's one automatic column grows to its widest item's content where a flex column stretches its items like a block, and it never takes an `items-*`: a container query's wrapper (`@container/hero`) and the chips' sideways bleed need the stretch. The dialog's own parts (`DialogText`, `DialogSeparator`, `DialogFooter`) keep margins on purpose: they sit at different depths inside a screen's forms and lists, and collapsing margins are what make that flow work. Margins that remain are inside one part (a row's text under its title), pushes (`mt-auto`), optical nudges (`[&_svg]:mt-px`) and paired negative margins that widen a hit area.
  - **A renamed class can change the cascade.** Tailwind orders its rules by variant, then by the properties they set (one that sets more comes before one that sets fewer), and only then by name, digit runs compared as numbers and `[` after digits but before letters. So `size-[15px]` becoming `size-3.75` moves it against the other digit-named and bracketed classes of that property (it came after `size-4`, now before), never against a letter-named one. That matters only where two of them reach one element: a part's base and a variant, or an `[&_svg]:size-*` holder inside another. The exact-rem change of 18 Nov 2026 was checked for it with a per-element computed-style dump before and after, besides the screenshots ([testing.md](testing.md)).
- With preflight on, nothing keeps a browser default but `strong`'s bolder weight and `small`'s smaller size: a heading states its size, weight and line height, a list its bullets (`list-disc`) or none, a raw element its margins. Every look lives in the component or page that draws it. The tokens that change with the screen's width (`--bar-h`, `--rail-w`) are in `tokens.css` with their media queries, inside `@layer theme`: unlayered, they would beat every layer. `theme.test.ts` checks the layer order in `app.css`, how each file is imported, and that every `:root` in `tokens.css` is inside `@layer theme`.
- Tailwind reads class names from core's `.ts` and `.tsx` files only (`@source` in `app.css`), so a utility class in a guide would build to nothing. Lint (`eslint-plugin-better-tailwindcss`, entry point `app.css`) keeps that from happening quietly: in core it rejects unknown, duplicate and conflicting classes and keeps their order and canonical spelling; in `apps/*/src` a `className` or `style` attribute is an error. It reads a `className`, a `cva` call and, by a selector in `eslint.config.js`, a constant named `<what>Classes` (a string, a template, or a map of them: `pressClasses`, `toneClasses`), so **a class list kept in a constant is named `<what>Classes`**. A guard in the same file backs that: in core's code (tests and stories aside) a module-level string or template constant is SCREAMING_CASE or a `…Classes` list, an error otherwise. It does not see a map or an array under another name, or a class list in SCREAMING_CASE: those rest on the name. A later `no-restricted-syntax` block for the same files replaces the guard's list rather than adding to it, so extend the one in `eslint.config.js`.
- A context becomes a prop (`size="compact"`, BulkCheck's `ownLine`) or a CSS variable the container sets (`--button-px`). Class conflicts inside one component (two `border-*` colours) aren't seen by lint when they sit in different strings: give each variant its own, and let a story check the computed colour.
- A class name that is also a Tailwind utility gets that utility's rules. Take care with names built at runtime, which lint can't see: the outline button once carried the class `outline`, and Tailwind's own `.outline` added a 1px outline to it.
- A colour that the contrast test checks has to be a hex value or exactly `color-mix(in srgb,var(--a) N%,var(--b))`, with no spaces after the commas. Anything else makes the theme test throw "not a colour this test can resolve". The test reads `tokens.css`, and also fails if any stylesheet in `packages/core/src` uses a `var(--…)` that neither the palette nor core defines.
- The build now writes an `@supports (color:color-mix(…))` fallback block for each `color-mix()` token, which the build before Tailwind didn't (about 0.7 KB gzipped more CSS per guide). `tailwindcss({ optimize: false })` doesn't change it, and which build pass adds them isn't verified. Every browser the guides support has `color-mix`, so the fallbacks never apply.
- Tailwind's `@tailwindcss/vite` plugin is left out of the jsdom tests, which never process CSS.
- After a style change, check every guide in the browser. They differ in palette, fonts, corners, layout and the length of their text ([testing.md](testing.md#in-a-browser)).

## Loaded on use

Base UI's popups, with the floating-ui code under them, came to about 56 KB gzipped of every guide's first download. They load on use now, in chunks of their own: the first download is 55.8 KB smaller, and 3.9 KB above where it was before Base UI, which is the sync client that landed since ([the numbers](#what-was-measured)).

- **What is lazy, and why those.** The dialogs (`DialogFrames.tsx`, with every screen in `screen-list.ts`, so the settings and any screen added later), the select (`select-impl.tsx`), the toasts (`Toasts.tsx`, Base UI's toast), the chapter drawer under 800px (`RailDrawer.tsx`, Base UI's drawer, which carries the dialog's code under it) and the icon buttons' tooltip (`Tooltips.tsx`, Base UI's tooltip with floating-ui's positioning). A page can be read without any of them, and floating-ui comes in with the first popup. In Koholint's build the toasts' chunk is 7.0 KB gzipped and shares 5.4 KB more with the dialog's. The chunks are listed in `components/chunks.ts`.
- **What stays eager: whatever is always on the page.** The collapsibles (route groups, the missables strip, the article's contents on a narrow screen) are Base UI in the entry, and they brought Base UI's shared helpers into the first download: about 9.6 KB gzipped in every guide. The rows' checkbox (`CheckBox.tsx`) is Base UI's `Checkbox` too, in the entry, and so are the buttons (`Button`), the chips (`ChipGroup`), the progress bars, the search field and the text field. When another part that is always on the page moves onto Base UI, it stays in the entry, and only the popups go in chunks. The tooltip shows how a popup with a trigger on every page splits: its triggers are Base UI's detached `Tooltip.Trigger`, tied to one handle (`tooltip-handle.ts`), which brings the hover and focus code and Base UI's popup store into the entry (about 11.5 KB gzipped in all, measured on Koholint's build); the tooltip that handle opens, with the positioning code, mounts from its chunk when the page is idle (`TooltipHost.tsx`), and the triggers join it without being redrawn, so a focused button keeps its focus. A pointer already resting on a button when it arrives opens it only the next time it comes onto the button (read in Base UI's source, where the hover starts on `mouseenter`). That keeps the code every page needs, Base UI's shared helpers included, in the first download, and the floating-ui code out of it.
- **What the row checkbox costs, and why it was kept.** Base UI's `Checkbox.Root` runs some 25 hooks and adds a span and a stand-in input per box, and Red Dead's checklist shows 307 of them. Measured on a production build of Red Dead, every chapter revealed, `/checklist`, Chromium at 6x CPU throttle, median of 10 (15 Nov 2026): the move from a native input (main at `7b0ca84`) took mounting the list on an in-app navigation from 242 to 335 ms (+38%) and a cold load until the rows are in from 279 to 352 ms (+26%). A click on a row went from 64 to 40 ms (Event Timing), because `RouteRow` is now memoised and only the ticked row redraws. The project's latency gate (a click under 200 ms, nothing more than 20% worse) failed on mount and load, and the owner chose Base UI anyway. Two things keep the cost down and must stay: each box gets its label's id as `aria-labelledby` (otherwise Base UI looks the label up after every render, and renders every box twice on mount), and each box has a `name` (without one Base UI pins its stand-in input to the viewport, and 307 of those cost a compositing pass on every tick, which took a click from 40 to 96 ms). Leaving out `Checkbox.Indicator` saved nothing measurable once the inputs had names.
- **One file per control, once the page shows it.** A module belongs to one chunk, so if the entry imports `controls.tsx` for one checkbox it takes the radio group, the code field and the file field with it. `controls.tsx` is for what the dialog's screens use. A control that a page shows on its own gets its own file, as `Select` did when it left `controls.tsx`.
- **Pages import a shell, never the module behind it.** `DialogHost.tsx`, `ToastHost.tsx` and `TooltipHost.tsx` (in `Layout`), `Layout` itself for the drawer, and `Select.tsx` import `chunks` and render what it loads; nothing outside `chunks.ts` imports `DialogFrames.tsx` or `select-impl.tsx`, except the dialog's own screens, which use `SelectImpl` directly (a shell inside the chunk would flash its stand-in). One stray static import puts the chunk back in the first download: after a change, check the entry in `dist/assets`.
- **`loadable.ts`, not `React.lazy`.** `loadable(() => import(…))` keeps a module once it has loaded and forgets a failure, so the next ask tries again. `useLoadable` returns the module, or undefined while it's on the way, and re-renders when it arrives. `React.lazy` needs a Suspense and an error boundary, and a lazy component whose import fails (a tab left open across a deploy asking for a file the new build has replaced, or no connection) takes the whole app down when nothing catches it. Here a failure is just a state, and a module that has already loaded renders at once, which is also what lets the tests stay synchronous.
- **When it loads.** `whenIdle` fetches the chunks once the page has loaded and the browser has a moment, so the page's own images and the reader's first taps never compete with them, and not at all for a reader who asked to save data. A select fetches its chunk sooner when the pointer or the focus reaches it. Safari has no `requestIdleCallback` (checked in Playwright's WebKit, the Safari 27.2 engine, where it's undefined; Chromium and Firefox have it), so a one-second timer stands in. The select's chunk is the largest (42.4 KB gzipped against the dialog's 17.6 KB in Koholint's build when there were two), because the dialog's settings screen uses the select and the code under both sits in `select-impl`; on every guide they arrive at about the same time, a second or so after the page loads. DialogHost warms the select's chunk along with its own, so a page that shows a select after a move (the checklist's filters) has the real one from the start, not the stand-in until the next idle moment. ToastHost warms the toasts' chunk, and loads it at once when a toast is wanted before then. The service worker precaches every chunk when it installs, so offline use and a tab left open on an old build keep working. What this saves is the first download and its parse, not the bytes a returning reader ends up with.
- **While a chunk is on the way.** The select shows its closed trigger drawn by hand (same size, label, value, so nothing moves). A tap or an arrow key on it is kept: the list opens when the select arrives, and the focus it had goes to the real trigger. A dialog asked for first loads its chunk on the spot and appears when it arrives, without the fade-in, which needs a dialog that was mounted closed. If a chunk the reader asked for can't come, a toast says why ("Reload the page to get the latest version" when online, since the likelier cause is a newer build; "Check your connection" when not), the dialog closes, and the next tap or opening tries again; a failed look-ahead is silent. The toast replaces an undo toast, which lasts seconds. A toast that can't be shown because the toasts' own chunk can't come is said in the page's status region instead, so a screen reader still hears it; a sighted reader then sees nothing, and the next toast asks for the chunk again.
- **Tests and stories load the chunks first.** `test/setup.ts` loads them in a `beforeAll` (after a test file's own `vi.mock`s are in place, since the dialog's chunk reads the guide), and `.storybook/preview.tsx` in a loader, so a test, and axe, meets the real components. `loading.test.tsx` mocks `chunks` to test what shows before they arrive; a story or test of a new lazy part needs the same two lines.

## Tests

- Core has no test script of its own: it can't run without a guide. Each app's Vitest runs its own `src/**/*.test.*` plus every test under `packages/core/src`, against that guide's config. A new shared test goes in `packages/core/src`, and runs three times.
- A test for one layout only: wrap it in `describe.runIf(config.layout === "article")`, as `App.test.tsx` does.
- **Raw CSS loads empty in Vitest unless it's let through.** `vite.ts` sets `test.css.include` to `/\.css\?raw$/`, so `?raw` imports get their text and any other CSS import gets nothing. Read a stylesheet as text with `?raw`. Before that line existed, the theme test had been passing on an empty string.
- `test.env.GUIDE_ROOT` is the app folder. `deploy.test.ts` uses it to read the app's `vercel.json` and compare it with the other apps', and `icons.test.ts` to read the app's icons.
- **jsdom is most of what a test file costs, so a file that never touches the DOM opts out.** Start it with `// @vitest-environment node` (`data`, `deploy`, `theme` and `progress-state` do), and the shims in `test/setup.ts` only run where there's a `window`. A file stays on jsdom if it, or anything it imports, reads `localStorage`, `location` or `document`: `boot.ts`, the stores, and so each guide's `guide.test.ts` (it imports `THEME_KEY` from `store/theme`). Under Node 26, `localStorage` in a node file is `undefined` with a warning, not an error, so a store's `try/catch` can hide it.
- **A file that mounts React calls `allowSlowMounts()` (`test/slow.ts`) before its tests.** A mount of the whole app takes 0.1 to 0.4 s on an idle machine, and ten to thirty times that with several checks running at once, which went past Vitest's 5 s default in `App.test.tsx` and `MissablesStrip*.test.tsx` (the first test of `App.test.tsx` took up to 13 s). The helper raises the test timeout to 60 s and Testing Library's `findBy`/`waitFor` wait to 30 s, in those files only. Both just catch a hang. Don't raise them in `vite.ts`.

## Before you commit

- `pnpm check` at the root runs lint, typecheck, tests and build for every package when core changes ([testing.md](testing.md#what-pnpm-check-runs)). Each app's typecheck includes core's source, so core is checked against every real config. A change to `GuideConfig` or `Brand` fails until every guide follows it.
- Check the change in a browser in at least one article guide (Koholint or Echoes) and Red Dead's checklist layout, on desktop and phone, in light and dark.
- Remember that every guide's site deploys from this one change. Check each preview before production ([deploying.md](deploying.md)).
